## 1. Назначение и границы

**Делает** — по карточке, architecture 3.7 spec:
- держит семантику формата модуля — одна библиотека на всех потребителей. Вердикт и проверка ключей при публикации зависят от одного кода видов проверки (R17 spec). При обновлениях R03 spec держат тест-векторы формата — `format/vectors/` `spec`: CI `spec` проходит их своей второй реализацией, а CI `module-kit` — все (R42 spec; repositories 3 spec);
- читает модуль автора — YAML 1.2.2 с ограничениями формата — и проверяет его по JSON Schema 2020-12 и правилам формата. Отказ называет ID правила (R45 spec). Что проверяется, перечисляет карточка:
  - схема, граф навыков без циклов, ссылки, навыки-опоры общей таксономии и зависимости паспорта (R49 spec, R50 spec);
  - задачи, проверки ячеек, каталоги ловушек и приёмов, уроки (R51 spec, R56 spec, R57 spec, R58 spec);
  - шаблоны со всеми экземплярами и их решателями (R60 spec, R61 spec);
  - тексты автора, которые ученик видит до решения, — проверкой утечки (concepts 10 spec; R57 spec).

  О картинке с прозрачными пикселями CLI предупреждает, но не отказывает (вторая поправка 2026-11-01 к R51 spec);
- читает версии формата модуля в окне. Пока формат v0, в окне только текущая версия, 0.2. Модуль проверяется, собирается и исполняется по версии, которую называет его паспорт, а модуль вне окна отклоняется с причиной (R44 spec);
- собирает пакет модуля и индекс модулей (R17 spec):
  - пакет — канонический вид с ярусом каждого навыка и числами каждого экземпляра шаблона, часть для устройства и опись (R62 spec);
  - индекс — из индекса прошлого релиза, с записью каждой опубликованной версии по дайджесту пакета и с отметками о снятии (R63 spec).

  Пакет — подписанная версия модуля, адресуемая по содержимому, индекс — подписанный накопительный список опубликованных версий (concepts 15 spec). На релизе `modules` их собирает CLI `module-kit` (repositories 4 spec);
- сравнивает новую версию модуля по правилам semver с опубликованными ниже неё, снятые тоже, — с новейшей всегда, — и сверяет упразднённые навыки: снятие ID навыков не освобождает (concepts 3 spec; R49 spec и поправка 2026-11-02 к нему). Через переход формата, пока формат v0, — только версию: навыки там держит ревью `modules` (раздел 3.5). Часть версии сравнение находит само, а у CLI для него своя команда `diff` (R13; раздел 3.5);
- заполняет шаблоны задач (concepts 9.3 spec; R60 spec):
  - перебирает сочетания параметров — не больше 10 000 на шаблон — и строит экземпляры;
  - ключ каждого экземпляра считает решатель ещё при проверке модуля (R61 spec);
  - экземпляр попытки выбирает генератор от её зерна (R59 spec; раздел 3.3);
- строит открытый вид задачи — без ключа, решения и ловушек — по пометкам `x-open` в схемах формата: поле без пометки закрыто (architecture 1 spec; R05 spec; R45 spec). Открытые виды он строит на сервере из части пакета для сервера, и в пакет они не входят (R62 spec);
- держит виды проверки и нормализацию: в формате v0 это `number`, `fraction`, `choice`, `predicate` и `rubric` (concepts 9.2 spec; R56 spec). Это код платформы, общий для всех модулей: модуль только выбирает вид и задаёт параметры (R02 spec);
- выносит вердикт: сравнивает наблюдение с ключом или условием (architecture 1 spec; concepts 9.1 spec; R03 spec). Вердикт допускается, только если ключ или условие дал автор, решатель или взрослый, а при ключе, выведенном ИИ, вердикта нет (concepts 9.4 spec; R04 spec);
- держит проверку утечки — поиск ключа и фраз-утечек, которые указал автор (concepts 10 spec; R57 spec). `api` проверяет ею текст наставника до того, как он уйдёт на устройство (architecture 3.5 spec), а проверка модуля — тексты автора (concepts 10 spec);
- исполняет Starlark в песочнице, как в standalone (repositories 7 spec):
  - условия проверки — не больше 1 000 000 шагов, а сработавший лимит или ошибка дают «без проверки» (R56 spec);
  - решатели шаблонов — не больше 100 000 000 шагов на все экземпляры шаблона (R61 spec).

  Часы, одновременные запуски и версия интерпретатора — раздел 3.4;
- сверяет пакет по цепочке дайджестов от индекса, который закрепил pull request `api`: индекс → опись → части → файлы (R62 spec, R63 spec). Подписей библиотека не проверяет: подпись файла релиза проверяет рецепт `spec` `release-verify` там, где файл входит в NovaTrail (R77 spec; поправка 2026-11-01 к R17 spec);
- даёт автору CLI: проверить модуль, собрать пакет, построить индекс и сравнить версии — `diff` (R13; раздел 3.5), — а сборке страницы образцов `canvas` отдаёт открытые виды и медиафайлы командой `open` (R15). Команды — раздел 3.6. Индекс CLI строит внутри общего релиза `modules`, после номера и до публикации (architecture 3.7 spec; R63 spec). «Собрать» пишет пакет файлами, а архив пакета для релиза кладёт рецепт `modules` (R03 modules). Снятия «построить индекс» читает файлом `withdrawals.yaml` `modules` — по `$defs/withdrawals` схемы индекса, которую принесёт T67 `spec`: в схеме v0.6.6 её ещё нет (architecture 3.7 spec).

**Не делает:**
- не обращается к ИИ (architecture 3.7 spec). Работу читает `tutor`, а `module-kit` получает от `api` уже наблюдение (architecture 1 spec; architecture 3.5 spec);
- не ходит в сеть: библиотека — вычисления без ввода-вывода, а CLI только читает и пишет файлы модуля (architecture 3.7 spec; repositories 1 spec). Прошлый индекс сборка получает файлом: его скачивает и проверяет общий релиз `.github` (поправка 2026-11-02 к R63 spec);
- не хранит данных учеников (architecture 3.7 spec): из частей платформы их на сервере хранит только `api` (architecture 1 spec; R15 spec);
- не владеет форматом. Схемы, текст формата, примеры и тест-векторы лежат в `format/` `spec` (R42 spec; R45 spec; repositories 5 spec), а `module-kit` держит семантику формата в коде (R17 spec). CI `spec` проверяет примеры валидатором JSON Schema, а векторы — своей второй реализацией, без `module-kit`: иначе `spec` зависел бы от того, кто зависит от него (repositories 3 spec);
- не задаёт генератор случайности и вывод зёрен. Их задаёт `spec`, с тест-векторами, а `module-kit` их проходит (architecture 1 spec). Генератор — PCG из `math/rand/v2` Go, а места случайности выводятся, как у стенда standalone (R59 spec). Они одни на всю платформу — на `module-kit`, виджеты, `engine` и `sim` (R27 spec);
- не подписывает пакеты и индекс и не проверяет подписей: подпись ставит общий workflow релиза из `.github`, а проверяет рецепт `spec` `release-verify` (R17 spec; R77 spec; repositories 4 spec);
- не выбирает урок или задачу и не считает модель ученика: это `engine` и `learner-model` (architecture 1 spec). Типы графа у них простые и не из `module-kit`: задаёт их `learner-model`, а `engine` берёт у него (architecture 3.8 spec; R28 spec);
- не публикует модули: реестр v0 — подписанный индекс, который собирает CI `modules`. Сервис реестра появится на этапе 4 и тоже будет построен на `module-kit` (R17 spec).

**Данные и связи:**
- своих данных нет: он работает с модулем, пакетом и индексом, которые ему дают. Данных учеников и секретов нет, как ни в одном репозитории (architecture 3.7 spec; RULES.md, Hard rules). В процессе `api` он получает наблюдение и ключ или условие задачи и возвращает вердикт (architecture 3.5 spec);
- при сборке ни от чего не зависит, кроме `spec` (repositories 2.1 spec; repositories 3 spec):
  - схемы, примеры и векторы формата он берёт модулем Go `github.com/altnovatrail/spec` — `spec.Format` по тегу релиза, тому же, что у подмодуля `spec/`, — а не из подмодуля;
  - типы частей, их открытых видов, канонического вида, описи и индекса — из пакетов `types/formatv0` и `types/formatv0/open` того же модуля (R64 spec, R72 spec);
  - тип наблюдения — из вложенного модуля Go `github.com/altnovatrail/spec/contracts`, который `spec` генерирует по контрактам API. Наблюдением `tutor`, `module-kit` и `api` обмениваются в одном процессе, и тип у него один (R83 spec). Контракт наблюдения пишет эпик E3 `spec`, строка 1.6 COORDINATION.md `spec`. Модуль `contracts` требует рантайм protobuf и connect-go (`contracts/README.md` `spec`): это сторонние модули Go, а не репозитории, и их лицензии проверит `ci-licenses`.

  Версию модуля `spec` в `go.mod` и подмодуль двигают вместе, переходом на тег, а из Dependabot `gomod` модуль `spec` исключают (R64 spec). Так же — вложенный модуль `spec/contracts`: его тег `contracts/vX.Y.Z` несёт номер тега `spec` (R83 spec). Придёт это с первым кодом, который читает формат: пока модуля `spec` в `go.mod` нет (Д46 в таблице 4 RUN.md `spec`). Это первый шаг эпика кода, E2 (R16);
- его импортируют `api` и eval-раннер `tutor`, а CLI по точному тегу берут CI `modules` и CI `canvas` — бинарником релиза, который сверяет `release-verify` до первого запуска (repositories 1 spec; repositories 3 spec; R77 spec). CI `canvas` берёт CLI, чтобы собрать страницу образцов: открытые виды и медиафайлы она получает при сборке, из пакетов релиза `modules` (R25 spec; architecture 3.2 spec). Для этого у CLI своя команда, `open` (R15; раздел 3.6). Позже, на этапе 4, на нём строятся `module-registry` и `module-pipeline` (architecture 3.7 spec; repositories 2.1 spec);
- `sim` его не берёт: часть пакета для сервера он читает по типам канонического вида из `spec` (architecture 3.9 spec; R62 spec). `learner-model` и `engine` пакетов не читают: граф им передаёт `api` (architecture 3.8 spec);
- вердикт воспроизводим. Попытка хранит дайджест своего пакета — дайджест описи, — версию формата модуля, версию `module-kit` и зерно. Вердикт повторяется по сохранённому наблюдению, без ИИ, тем релизом `module-kit`, который его вынес (architecture 1 spec; R03 spec; R44 spec). Изменение поведения вида проверки — новая версия формата (R44 spec);
- новую модель ИИ допускают по eval, и ложные тревоги там считаются по вердикту, через `module-kit` (architecture 4.6 spec; repositories 4 spec);
- проверки CI пришли ещё до кода: общие проверки из `.github`, среди них `docs-check-repo`. Какие они и что держит мерж — R30 spec и architecture 3.11 spec. Подключила их T17 `spec`, и файлы CI сюда писала её сессия; файлы CI под свой код пишет сессия этого репозитория (поправка 2026-10-21 к R30 spec).
  - Находки CodeQL, Scorecard и SonarCloud закрываются перед новой задачей (правило 12 [RUN.md](../RUN.md)), а общие для всех репозиториев причины тех, что остаются открытыми, записаны в R33 spec.
  - Проверки Go пришли с заготовкой CLI (R04): рецепты у них свои, а запускает их обёртка Go — общий `go.yml` `.github`, который на ней и проверен (R16 .github). Go CodeQL читает с T12: общий `codeql.yml` `.github` v0.1.3 собирает его с Go из стадии `toolchain` (R06). Обёртка TypeScript проверяется на первом коде на TypeScript, у `canvas` (repositories 6 spec; architecture 3.11 spec).
  - Релиз выпускает общий `release.yml` `.github`, а файлы для него собирает свой рецепт `release-files` (R07; раздел 3.1).
  - Код приходит со своими тестами, а когда покрытие пойдёт в Codecov, мерж будет ждать `codecov/patch` (RULES.md, How we work; R48 spec) — Д8 в таблице 4 [RUN.md](../RUN.md);
- этап 1, вместе с `modules`: формат модуля сразу проверяется на трёх модулях двух предметов (repositories 6 spec; R08 spec; R41 spec; product 11 spec). Работу по порядку repositories 6 spec ведёт сквозной план — COORDINATION.md `spec`; у `module-kit` там строки 3.1–3.3: переход на линию 0.6, детализация и эпик кода (R76 spec).

## 2. Решить при детализации

Пункты «Решить при детализации» из карточки — по подразделу на пункт. Каждый, кроме 2.6, решает своя задача эпика E1 в [RUN.md](../RUN.md). Решённый пункт называет запись журнала, а само решение переезжает в раздел 3. Вопрос, который выходит за этот репозиторий, уходит «в реестр spec» (RULES.md, Across repositories).

У карточки четыре пункта — подразделы 2.1–2.4. С v0.6.3 три первых — не вопросы о формате, а то, что формат оставил `module-kit`: чем писать канонический текст пакета, как CI проходит векторы генератора, часы и одновременные запуски Starlark (architecture 3.7 spec; R08). Четвёртый, сравнение версий по semver, карточка получила в v0.6.4 (поправка 2026-11-02 к R49 spec; R12): формат задаёт для него только мажорную версию и таблицу соответствия (concepts 3 spec; R49 spec), а раньше его называла только задача, которая завела репозиторий (T05 `spec`). Подраздел 2.5 — сверх карточки: его вопрос `spec` по-прежнему оставляет детализации `module-kit` (поправка 2026-10-28 к R25 spec). Карточку под пункт сверх неё правит итог детализации, T05, — строкой таблицы 3 «в реестр spec», когда решение уже принято (architecture 3 spec). Подраздел 2.6 — то, что эпик кода ждёт от `spec`.

С T05 все пять пунктов решены — R09, R10, R11, R13 и R15. Сознательно отложены память стороннего Starlark (2.3), шаблоны и дайджест открытого вида в команде `open` (2.5) и тип наблюдения (2.6).

На v0.2.13 два первых пункта были вопросами реестра `spec`, Т-15 и Т-18, и T01 и T02 должны были принести к ним варианты. Эпик формата E2 `spec` их не дождался: Т-15 закрыл R62 spec, Т-18 — R59 spec, и обе задачи сужены (R08).

### 2.1. Пакет модуля и канонический текст

- **Суть:** как `module-kit` собирает пакет модуля по R62 spec и чем пишет его канонический текст. Состав пакета решил формат, а здесь решалось, как его исполнить.
- **Решено** (R09): канонический текст пишет своя функция, которая останавливается на значении вне формата, а канонический вид собирается из JSON-значения каждого файла как есть. Устройство пакета — раздел 3.2.
- **Задача:** T01.

### 2.2. Генератор в CI

- **Суть:** чем `module-kit` исполняет генератор и места случайности по R59 spec — стандартной библиотекой Go или своим кодом — и как его CI проходит векторы `format/vectors/random/` `spec`.
- **Решено** (R10): генератор — свой код по константам [текста формата](../spec/format/README.md), раздел 22, с ошибкой на аргументе вне области, а `math/rand/v2` и `hash/fnv` — только эталон в тестах. Генератор лежит в `internal/`, а наружу идёт выбор экземпляра попытки. Устройство — раздел 3.3.
- **Задача:** T02.

### 2.3. Часы, одновременные запуски и память Starlark

- **Суть:** сколько времени у вычисления условия проверки и у решателя шаблона, сколько их идёт сразу, кто держит часы и места, что значат сработавшие часы, сколько памяти у песочницы и нужен ли отдельный процесс. Шаги, диалект и место решателя решил формат, а часы и одновременные запуски он оставил `module-kit` (architecture 3.7 spec).
- **Решено** (R11): go.starlark.net — той версии, которую назовёт формат, а сейчас последней. Часы — страховка `module-kit`: 1 с на условие и 60 с на решатель шаблона. Мест библиотека не держит, одновременность — у вызывающего, а диалект условия — тот же, что у решателя. Устройство — раздел 3.4.
- **Отложено:** память стороннего Starlark. С этапа 4 условия в `api` и решатели в `module-registry` пишут и сторонние авторы (О-9), а go.starlark.net памяти не считает. Нужен процесс с лимитом памяти, и решать это `api` и `module-registry` — В12 в таблице 3 [RUN.md](../RUN.md), «в реестр spec». До тех пор — Д10 в таблице 4 [RUN.md](../RUN.md).
- **Задача:** T03.

### 2.4. Правила semver для `diff`

- **Суть:** по каким правилам `module-kit` сравнивает новую версию модуля с прошлой: что поднимает мажорную, минорную и патч-версию, что сравнение находит само, а что объявляет автор. С v0.6.4 карточка называет сравнение среди пунктов «Решить при детализации»: новая версия сравнивается с каждой опубликованной ниже неё по semver, снятые тоже (architecture 3.7 spec; R12). Раньше его называла только задача, которая завела этот репозиторий (T05 `spec`). Команды `diff` в карточке нет: CLI там — «проверить, собрать, построить индекс». Отдельная это команда или часть проверки, решает задача.
- **Решено** (R13): сравнение само находит наименьшую часть версии, а автор может поднять выше, но не ниже. Мажорная — когда что-то из того, что было у ученика прошлой версии, ушло или значит другое. Сравниваются пакеты: с новейшей опубликованной версией всегда и с остальными, если их дали, снятые тоже, а через переход формата, пока `spec` не ответит на В15, — только рост версии. У CLI для сравнения своя команда, `diff`. Таблица «изменение — часть версии», правила сравнения и команда — раздел 3.5.
- **В реестр spec:** правила сравнения и таблица — в текст формата, В14; места, которые формат держит во всех версиях, и все опубликованные версии в CI `modules` — В15 (таблица 3 [RUN.md](../RUN.md)). На В3 `modules` `spec` ответил в v0.6.6, не застав В15 (R14).
- **Задача:** T04.

### 2.5. Команда CLI для открытых видов

- **Суть:** нужна ли CLI `module-kit` своя команда, которая отдаёт открытые виды задач сборке страницы образцов `canvas`, или этой сборке хватает команд карточки — проверить, собрать, построить индекс (architecture 3.7 spec). Вопрос R25 spec оставил детализации `module-kit`, и поправка 2026-10-28 к R25 spec оставила его там же. Решается здесь: CLI — часть `module-kit` (R17 spec). Новая команда меняет карточку, и её правку итог детализации отправляет строкой таблицы 3 «в реестр spec» (раздел 2).
- **Решено** (R15): своя команда `open` на релиз `modules`. Она пишет файл открытых видов — у каждого модуля по его новейшей неснятой версии ID, версию, дайджест пакета, открытые виды паспорта и задач, как в `tutor-open-tasks`, — и медиафайлы задач, `LICENSE` и `NOTICE`, сверенные по описи. Снятые версии она пропускает. Строится после протокола eval, вне первого релиза. Устройство — раздел 3.6.
- **Отложено:** что `open` отдаёт у шаблона и дайджест открытого вида каждой задачи. Оба решит протокол eval — эпик E3 `spec`, строка 1.6 COORDINATION.md `spec`. Варианты у шаблона — экземпляр по зерну, как просит `canvas` (architecture 3.5 canvas); экземпляры по номерам; все экземпляры. У дайджеста — SHA-256 канонического текста открытого вида, как предлагает В67 `tutor`. Вопрос — В17 в таблице 3 [RUN.md](../RUN.md), «в реестр spec».
- **Задача:** T05.

### 2.6. Тип наблюдения

- **Суть:** вердикт `module-kit` выносит по наблюдению — тому, что `tutor` прочитал в работе (architecture 3.5 spec). Наблюдением `tutor`, `module-kit` и `api` обмениваются в одном процессе, и тип у него один — код, который `spec` генерирует по контрактам во вложенный модуль Go `spec/contracts` (R83 spec).

До него вердикт библиотеки берёт прочитанные значения ячеек — то, что текст формата называет «the value read», а «не прочитать» и «без проверки» по чтению — то, что наблюдение скажет сверх значений ([текст формата](../spec/format/README.md), раздел 15). Придёт контракт — задача эпика кода свяжет вердикт с типом наблюдения, а модуль `spec/contracts` исключит из Dependabot `gomod`, как модуль `spec` (раздел 1).

### 3.2. Пакет модуля

Пакет собирает CLI на релизе `modules`, из папки модуля, по версии формата, которую называет его паспорт ([текст формата](../spec/format/README.md), раздел 25; R62 spec). Пакет собирается только из модуля, который прошёл проверку: схему и все правила формата (R45 spec). Код пишет эпик кода (R09).

- **Части пакета** (concepts 15 spec):
  - часть для сервера — канонический вид, `server.json`: модуль одним JSON-объектом, со всем содержанием, и ключами, решениями и ловушками тоже;
  - часть для устройства — `LICENSE`, `NOTICE` и медиафайлы, а когда в формате будут виджеты, — их бандлы. Её называет список, `device.json`;
  - опись — `inventory.json`: версия формата, ID и версия модуля и обе части по дайджестам и размерам. Это не паспорт модуля, хотя паспорт в коде и схемах называется `manifest`.
- **Как он собирается:**
  1. Читатель YAML даёт JSON-значение каждого файла части (R45 spec). Файлы и папки на `.`, комментарии и `eval/` в пакет не идут.
  2. Канонический вид: части модуля — под своими членами, `manifest`, `skill_graph`, `traps`, `techniques` и `solving_steps`, а `tasks` и `lessons` — объектами по локальному ID. Значение части — JSON-значение её файла как есть: шаблон — как написан, и значений по умолчанию нет (R09). Сверх частей — `skill_tiers`, ярус каждого навыка, по [тексту формата](../spec/format/README.md), раздел 12, если у модуля есть граф навыков, и `instances`, числа и результаты решателя каждого экземпляра шаблона, по [тексту формата](../spec/format/README.md), разделы 23 и 24, если среди задач есть шаблоны. Члена без своей части — и `skill_tiers` без графа навыков, и `instances` без шаблонов — в виде нет. Целое, которое читатель YAML дал как double, — `50.0` или `5e1`, — идёт в вид целым `50` ([текст формата](../spec/format/README.md), раздел 25).
  3. Список части для устройства — объект: `license` — дайджест и размер `LICENSE`; `notice` — `NOTICE`, только если он есть; `media` — каждый файл `media/` по пути от `media/`, только если такие файлы есть (`inventory.schema.json`, `$defs/device_listing`).
  4. Опись: `module_format_version`, `id` и `version` — как в паспорте, а `server_part` и `device_part` — дайджест и размер канонического текста канонического вида и списка.
  5. Дайджест пакета — дайджест канонического текста описи. Пакет файлами — папка: `inventory.json`, `server.json` и `device.json` — канонические тексты описи, канонического вида и списка, — и `device/` с `LICENSE`, `NOTICE` и `media/<путь>` побайтно. Так их пишет «собрать», а архив пакета для релиза кладёт рецепт `modules` (R03 modules; architecture 3.7 spec).

  Пакет зависит только от файлов модуля и версии формата его паспорта: версии `module-kit`, времени и путей в нём нет (R62 spec).
- **Канонический текст** пишет своя функция над деревом JSON-значений — объект, массив, строка, целое, `true`, `false`, `null` (R09):
  - члены объекта идут по порядку кодовых единиц UTF-16 их имён, а между лексемами пробелов нет;
  - целое пишется десятичными цифрами, отрицательное — со знаком `-`;
  - в строке экранируются только `"` и `\`, `\b`, `\t`, `\n`, `\f` и `\r`, а прочие знаки до U+001F пишутся как `\u00` и две строчные шестнадцатеричные цифры. `<`, `>`, `&`, U+2028 и U+2029 пишутся как есть, и знаки не нормализуются;
  - текст — UTF-8, без BOM и без перевода строки в конце;
  - на числе с дробной частью, целом вне ±(2^53−1), строке не из корректного UTF-8 и значении не из JSON функция останавливается с ошибкой. На проверенном модуле такой отказ значит дефект в коде `module-kit` (R09). Тексты пакета и индекса модулей пишет только она: не `encoding/json`, не `jsontext` и не проход по типам `formatv0`.
- **Дайджест** — `sha256:` и 64 строчные шестнадцатеричные цифры от байтов, а размер — их число (concepts 15 spec). Дайджест пакета хранит попытка (architecture 1 spec).
- **Чтение пакета** идёт по цепочке дайджестов от дайджеста пакета, который закрепил индекс: опись → части → файлы. Подписей библиотека не проверяет (R62 spec, R63 spec, R77 spec).
- **Кто читает пакет:**
  - через `module-kit` — `api`, по дайджесту, и eval-раннер `tutor`, а с этапа 4 — `module-registry` (architecture 3.10 spec; R17 spec);
  - через CLI `module-kit` — CI `canvas`, для страницы образцов (R25 spec);
  - без `module-kit` — `sim`, по типам канонического вида из `spec` (architecture 3.9 spec);
  - часть для устройства раздаёт `api` (architecture 3.10 spec).
- **Где лежит:** на этапе 1 пакеты и индекс лежат в релизах `modules`, на этапе 2 пакеты лежат и в образе `api`. Для повтора вердикта старые версии пакетов берутся из релизов `modules` (architecture 3.10 spec; Т-17).
- **Тесты:**
  - все векторы `format/vectors/packages/` и `format/vectors/tiers/` из `spec.Format` (R64 spec). Результаты решателя вектора `with-solver` CI считает своим запуском (Д44 в таблице 4 RUN.md `spec`);
  - модульные тесты таблицы экранирования и каждого отказа;
  - fuzz-тест, который сверяет функцию с `jsontext.Value.Canonicalize` на значениях, допустимых в формате. Он лежит в файле с `//go:build goexperiment.jsonv2`, и при `GOEXPERIMENT=nojsonv2` остальные тесты идут без него (R09).

### 3.3. Генератор и места случайности

Генератор и места случайности `module-kit` исполняет по [тексту формата](../spec/format/README.md), раздел 22 (R59 spec), своим кодом (R10). Код пишет эпик кода.

- **Пакет** — `internal/random`: в API библиотеки он не входит, и другие модули Go его не импортируют. Генератор один на платформу по алгоритму, а не по коду: `engine`, `sim` и виджеты исполняют его сами и проходят те же векторы (R27 spec; R59 spec).
- **Поток** — два слова состояния, старшее и младшее, взятые как есть. Шаг — `state · M + C mod 2^128` через `bits.Mul64` и `bits.Add64`, выход — DXSM, а константы — числами из текста формата. Общего состояния нет: поток живёт в одном вызове.
- **Место случайности** — зерно, целое без знака в 64 бита, и список имён. Его поток начинают два слова: FNV-1a 64 от UTF-8 текста «зерно десятичными цифрами, затем `|` и имя — для каждого имени» и само зерно. Имён хотя бы одно, а имя — непустая строка из корректного UTF-8 без `|`; иначе место не строится, а возвращается ошибка. Так же, на `math/rand/v2` и `hash/fnv`, выводит поток `seeded` стенда standalone — место главного зерна с именами «эксперимент, единица, назначение», — а в рабочем коде standalone генератора от зерна нет (R59 spec; раздел 4).
- **Функции** — пять, те, что проверяют векторы. Каждая берёт столько целых, сколько велит текст формата:

  | Функция | Область | Как считает |
  |---|---|---|
  | `integer` | — | следующее целое потока |
  | `below(b)` | b от 1 до 2^64 − 1 | степень двойки — маской; иначе метод Лемира: старшее слово произведения целого на b, с отбраковкой, пока младшее слово меньше (2^64 − b) mod b |
  | `between(a, c)` | a ≤ c и c − a + 1 ≤ 2^63 − 1. Сначала проверяется a ≤ c, а затем, без переполнения, что `uint64(c) − uint64(a)` не больше 2^63 − 2 | a + `below(c − a + 1)` |
  | `fraction` | — | младшие 53 бита следующего целого, делённые на 2^53 |
  | `permutation(n)` | n от 0 до 2^31 − 1 | от 0, 1, …, n − 1 по порядку, а для i от n − 1 до 1 — обмен мест i и `below(i + 1)` |

  На аргументе вне области функция возвращает ошибку и целых не берёт. Тасования списка нет: векторов у него нет, а `module-kit` ничего не тасует (R10).
- **Экземпляр попытки** — одна функция API шаблонов: номер `below(count)` места зерна попытки с именами `template`, ID задачи и `instance`, при count от 1 до 10 000 (R60 spec; [текст формата](../spec/format/README.md), раздел 23). Других вызовов это место не делает, а других мест у модуля в формате v0 нет. ID задачи — строчные латинские буквы, цифры и `-` (`common.schema.json`), и имя места из него всегда допустимо. Зерно попытки берёт `api` из криптостойкого источника, а `module-kit` получает его числом. Ни зерно, ни слова места на устройство не уходят: по словам видно зерно ([текст формата](../spec/format/README.md), раздел 22).
- **Чего в коде нет:** случайности не от зерна — ни `math/rand`, ни функций верхнего уровня `math/rand/v2`, ни `crypto/rand`. `math/rand/v2` и `hash/fnv` есть только в тестах.
- **Тесты:**
  - все векторы `format/vectors/random/` из `spec.Format` (R64 spec). Вектор читают читатель YAML и валидатор схем проверки модуля — по `random-vector.schema.json` — и тип `formatv0.RandomVector` (R72 spec), а числа-строки разбирает `strconv`. Если даны зерно и имена, выведенные слова сравниваются с `state`. Затем вызовы идут по порядку, и каждое значение сравнивается, `fraction` — как double. Тест падает, если векторов нет и если у вызова нет известного поля;
  - место шаблона проверяют и векторы `format/vectors/templates/`: по каждому зерну они называют экземпляр;
  - модульные тесты — каждый отказ и число целых, которое берёт каждая функция: `below(1)` и `between(a, a)` берут одно, `permutation(0)` и `permutation(1)` — ни одного;
  - сверка со стандартной библиотекой: поток, функции и слова места сравниваются с `math/rand/v2` и `hash/fnv`. Обычный тест идёт на каждом `go test` — на словах всех векторов, на границах 1, степенях двойки, 2^63 − 1, 2^63 + 1 и 2^64 − 1 и на нескольких тысячах входов от самого генератора с постоянным зерном. Fuzz-тест сверяет то же на любых входах, с перестановками до 1024 чисел, и те же входы лежат в его корпусе. Эталон живёт только в тестах, и тега сборки им не нужно (R10).

### 3.4. Песочница Starlark

Starlark формата — условия проверки, выражения шаблонов и решатели — `module-kit` исполняет в go.starlark.net, в процессе вызывающего (R11). Код пишет эпик кода.

- **Лимиты:**

  | Лимит | Что держит | Кто держит | Откуда число |
  |---|---|---|---|
  | условие — не длиннее 1000 знаков | размер выражения | проверка модуля, по схеме | формат (R56 spec) |
  | условие — не больше 1 000 000 шагов | шаги одного вычисления в счёте закреплённой версии go.starlark.net | `Thread.SetMaxExecutionSteps`; сработал — «без проверки» | формат (R56 spec) |
  | часы условия — 1 с | время вычисления, чьи шаги зовут тяжёлые встроенные функции | `module-kit`, константа релиза; сработали — «без проверки» | замер 2026-11-02: простое условие тратит на 1 000 000 шагов 6 мс (R11) |
  | выражение шаблона — не длиннее 1000 знаков, шагов не больше, чем лексем; сочетаний — не больше 10 000 на шаблон | цена перебора экземпляров | проверка модуля: длина — по схеме, сочетания — правилом `task.template-instances` | формат (R60 spec) |
  | решатель — не длиннее 8192 знаков | размер программы | проверка модуля, по схеме | формат (R61 spec) |
  | решатель — не больше 100 000 000 шагов на шаблон | шаги верхнего уровня и всех вызовов `solve` в том же счёте | `Thread.SetMaxExecutionSteps` на одном потоке шаблона; сработал — нарушение `task.template-solver` | формат (R61 spec) |
  | часы решателя — 60 с на шаблон | время программы, чьи шаги зовут тяжёлые встроенные функции | `module-kit`, константа релиза; сработали — нарушение `task.template-solver` | замер 2026-11-02: простой цикл тратит на 100 000 000 шагов 0,45 с (R11) |
  | рекурсия выключена | стек Go от рекурсии функций Starlark: его переполнение роняет весь процесс | диалект, `Recursion: false`; go.starlark.net ловит и рекурсию через `lambda`. Встроенные функции на глубоко вложенных значениях она не держит — их держит, как и память, только отдельный процесс | формат: у решателя — R61 spec, у условия — В11 |
  | одновременные запуски | CPU процесса и стенное время часов | вызывающий: `api` — не больше vCPU сразу, CLI — решатель на CPU | R11; у `api` — В13 |
  | паника интерпретатора | процесс вызывающего | `module-kit`, `recover`: «без проверки» или нарушение `task.template-solver` | R11; #672 go.starlark.net |
  | память | процесс вызывающего | до этапа 4 — никто: go.starlark.net её не считает | Д10; В12 |
  | версия go.starlark.net | счёт шагов и поведение языка | формат называет её, `module-kit` закрепляет в `go.mod` | В10; пока — 4f4267fb140d (R11) |

  Шаги считает go.starlark.net той версии, которую закрепил `module-kit`: с 2026-10-05 счётчик растёт на 10 за обратный переход или вызов, а раньше рос на 1 за инструкцию (раздел 4). Тот же модуль на тех же значениях делает те же шаги на любой машине, но не в другой версии интерпретатора: поэтому версию назовёт формат.
- **Вызов.** Вычисление идёт синхронно, в потоке вызывающего, на своём `starlark.Thread` и с `context` вызывающего. Часы `module-kit` и отмена `context` зовут `Thread.Cancel` с разными причинами. Первые дают «без проверки» или нарушение правила, вторая — ошибку без вердикта. Отмену интерпретатор видит между инструкциями, а встроенную функцию не прерывает: `len(list(range(50000000)))` при часах 100 мс останавливается через 0,2 с после них, взяв 763 МиБ, а `str` списка глубиной 1 000 000 идёт больше 120 с на одном шаге (R11). Часы идут по стенному времени, поэтому вызывающий держит одновременных вычислений не больше, чем у него vCPU (В13). Мест и общего состояния у песочницы нет.
- **Диалект** — один на весь Starlark формата, как в [тексте формата](../spec/format/README.md), раздел 24: `Set`, `While`, `TopLevelControl` и `GlobalReassign` включены, `Recursion` выключена, `load` запрещён. Условие — в нём же; пока формат этого не сказал, это В11.
- **CLI** проверяет решатели шаблонов по одному на CPU (`GOMAXPROCS`), каждый на своём потоке Starlark, а итог выводит в порядке шаблонов. Шаги потока от соседей не зависят. Стенное время и память у решателей общие: тяжёлые встроенные функции нескольких шаблонов сразу дойдут до часов или до предела памяти раньше, чем по одному.
- **Что известно из standalone** (раздел 4):
  - 25 000 000 шагов и 2 с на запуск, по одному запуску на vCPU и 3 с ожидания места; лимит шагов калибровали по 450 эталонным решателям, и худший потребовал 2 081 362 шага (R53 standalone);
  - его помощники платят шаг за каждые 16 байт и не строят списков длиннее 1 000 000 элементов: так шаги ограничивают и память помощников — 381 МиБ на потолке шагов, — а среде Go отдана девять десятых памяти экземпляра (`GOMEMLIMIT`);
  - но дыра памяти шире одного оператора. Оператор `*` и повторное `xs = xs + xs` строят огромный список мимо счётчиков; литерал `{}` в цикле держит по 512 байт на каждые девять шагов, и экземпляр с 1 ГиБ памяти был убит именно так; методы самих значений — `x.extend(range(3000000))` — берут три миллиона элементов за девятнадцать шагов (SPEC 6.6 standalone; R53 standalone);
  - отдельный процесс v1 standalone отложил, а четыре места с часами-страховкой отверг: «Verdicts depend on the load» (R125 standalone);
  - самый тяжёлый из его решателей — 2 413 617 шагов на версии standalone и 2 725 355 на 4f4267fb140d (R11).
- **Отложено:** память стороннего Starlark с этапа 4 — раздел 2.3.

### 3.5. Сравнение версий модуля

Новую версию модуля `module-kit` сравнивает с опубликованными версиями ниже неё по semver, снятые тоже: с новейшей всегда, а с остальными — если их дали (architecture 3.7 spec; поправка 2026-11-02 к R49 spec; поправка 2026-11-02 к R13). Сравнение само находит наименьшую часть версии, которую надо поднять, а автор может поднять и выше, но не ниже (R13). Версия модуля — semver `X.Y.Z` без пред-релизов и метаданных сборки (R46 spec); это не версия формата, MAJOR.MINOR, которую называет `module_format_version` (R44 spec). Код пишет эпик кода.

- **Принцип.** Версия модуля говорит, что стало с тем, что было у ученика прошлой версии:
  - **мажорная** — что-то ушло или значит другое: удалена запись с полным ID — навык, задача, урок, ловушка или приём, — сужена аудитория, навык больше не учит навыку-опоре, изменилась проверка у задачи, которая осталась, или модуль перешёл на версию формата, которая может изменить вердикты. Сюда же — то, что называет concepts 3 spec;
  - **минорная** — всё, что было, осталось и значит то же, а модуль даёт больше или ведёт иначе: новые записи, пререквизиты, полосы и сложность задач, шаги решения;
  - **патч** — те же записи, проверки и путь, другие слова или картинки.

  Внутри одной мажорной у ученика ничего не пропадает, и `api` может переводить его на новую версию сам; какую версию получает новая попытка, решает `api` (architecture 3.5 spec). Смену смысла записи по модулю не видно: автор объявляет её новым ID — у навыка так велит R49 spec, а у задачи, урока, ловушки и приёма это то же удаление и новая запись. Других объявлений у автора нет: номер версии — и есть его объявление.
- **Что сравнивается** — пакеты, а не YAML автора: канонический вид и список части для устройства (раздел 3.2). Новая версия — папка модуля, которую `diff` проверяет и собирает в памяти, или пакет, уже собранный `build`. Опубликованные версии — пакеты файлами, каждый сверен по цепочке дайджестов от индекса. Что в пакет не входит — комментарии, порядок ключей, `eval/`, файлы на `.`, — версии не меняет: пакет тот же.
- **Таблица «изменение — часть версии»** — по полям схем формата 0.2. «Выбор» — строки, где принцип оставляет место суждению: автор вычитывает их построчно.

- **Проверка, которая решает вердикт и ловушку,** сравнивается по смыслу, как её читает вид проверки ([текст формата](../spec/format/README.md), раздел 15):
  - `number` — ключ как рациональное число и набор `units` после шагов 1–5 нормализации и строчных букв;
  - `fraction` — ключ как рациональное число и `form`, `any` по умолчанию;
  - `choice` — ключ и набор вариантов — своих у проверки или у ячейки с привязкой `choice` — после нормализации выбора;
  - `predicate` — строка условия, как написана: равенство условий Starlark в общем случае не решить;
  - значения ловушек — набор пар «значение, как его сравнивает проверка, — ловушка»; текст ловушки — слова;
  - `kind` — всегда.

  Так `"2.50"` и `"2.5"`, `"6/8"` и `"3/4"` при `form: any` или переставленные значения ловушек — не изменение. Добавленная единица — изменение: какой-то ответ, который не читался, получает вердикт.
- **Шаблон** — задача, у которой проверка своя у каждого экземпляра. У задачи, которая шаблон в обеих версиях:
  1. другие имена параметров — мажорная: экземпляры не сопоставить;
  2. экземпляры сопоставляются по значениям параметров, а не по номерам: порядок и число экземпляров, новые производные числа и результаты решателя сами по себе ничего не значат;
  3. у каждого сопоставленного экземпляра заполнители заменяются числами из `instances` его версии ([текст формата](../spec/format/README.md), раздел 23), и проверки сравниваются, как выше. Разница — мажорная, и отчёт называет числа экземпляра;
  4. экземпляр только в одной из версий — минорная, с пометкой «выбор»: ученик получал задачу, а не экземпляр, и попытка держит свой пакет и своё зерно.

  Выражения, ограничение и решатель своей части не дают: они действуют только через числа экземпляров. Число, которое видно лишь в условии задачи, — слова. Starlark сравнение не запускает: результаты решателя уже лежат в `instances`.
- **Правила сравнения** — ID предложены `spec`, В14 в таблице 3 [RUN.md](../RUN.md):

  | ID | Правило |
  |---|---|
  | `manifest.version-above` | (а) Новая версия выше каждой опубликованной версии модуля по semver, снятые тоже. Версия новейшей опубликованной с тем же дайджестом пакета — модуль не изменился, сравнивать нечего; с другим дайджестом — отказ `module-index.one-package`. Версия ниже новейшей или равная другой опубликованной — отказ: папка модуля пошла назад. Исправлений старой линии нет: в папке модуля одна линия версий (T01 modules), а снятую новейшую исправляет версия выше неё (вторая поправка 2026-11-02 к R63 spec). |
  | `manifest.version-step` | (б) Новая версия — следующая по одной из частей после новейшей опубликованной: X.Y.(Z+1), X.(Y+1).0 или (X+1).0.0, — и эта часть не ниже найденной. У 0.y.z, как в Cargo, мажорную играет y, а минорную и патч — z. У 0.0.z каждая версия — своя мажорная: любая правка поднимает z, и двух версий 0.0.z одной мажорной нет. Первая версия, с `--first`, — любая: сравнивать её не с чем. |
  | `skill-graph.retired-complete` | (в) Каждый навык каждой опубликованной версии ниже есть в `skills` или в `retired_skills`. |
  | `skill-graph.retired-kept` | (г) Каждая запись `retired_skills` новейшей опубликованной версии есть и в новой, а её `replaced_by` — то же раскрытие: навык, который остался, стоит как есть, а навык, упразднённый позже, заменён своим `replaced_by` в новой версии. Сравниваются наборы. |
  | `skill-graph.retired-known` | (д) Новая запись `retired_skills` называет навык какой-нибудь опубликованной версии ниже. Так версия до `diff`, которая уронила навык молча, поправляется: новая версия его упраздняет. Если `diff` дали не все версии, запись, которую данные версии не подтверждают, не отказ — её называет отчёт. |
  | `module.ids-kept` | (е) ID навыка, задачи, урока, ловушки или приёма опубликованной версии ниже, которого нет в новейшей опубликованной, в новой версии не появляется — ни среди её записей, ни в `skills`: ID не называет другую запись. Навык, упразднённый как положено, держит и `skill-graph.retired-ids`, а это правило ловит и навык, который уронила молча версия до `diff`. |
  | `manifest.languages-kept` | (ж) `languages` — те же: модуль на другом языке объяснения — другой модуль. |

  Снятая версия в сравнении — опубликованная, а `withdrawn` сравнение не читает (поправка 2026-11-02 к R49 spec). Исправление снятой стоит выше неё и почти всегда мажорное: правка ключа сама мажорная (вторая поправка 2026-11-02 к R63 spec).

  Новейшая опубликованная версия нужна всегда: по ней `diff` находит часть версии и проверяет правило (г). Правила (в), (д) и (е) он проверяет по всем опубликованным версиям, которые ему дали, а CI `modules` пока даёт одну новейшую: по карточке 3.7 spec её хватает, потому что в `modules` одна линия версий и правило «ни одна запись не пропала» переносит навыки всех версий ниже. Правило (д) по неполному набору не отказывает: запись, которой данные версии не подтверждают, отчёт называет, и только. Навык, которого нет ни в `skills`, ни в `retired_skills` текущей версии, `learner-model` не переносит никуда, и ошибки при этом нет (поправка 2026-11-02 к R80 spec). Поэтому `module-kit` предлагает `spec` все версии и постоянные места — В15 в таблице 3 [RUN.md](../RUN.md): по одной новейшей правило (е) видит только ID, ушедшие в ней, а через переход формата навыки не сверяет никто (поправка 2026-11-02 к R13).
- **Переход формата.** Пока формат v0, CLI читает только текущую его версию (R44 spec). Через переход `diff` проверяет только версию — правила (а) и (б): новая выше всех опубликованных и мажорная, потому что часть версии при переходе — мажорная. Версию формата прошлой он берёт из записи индекса, где она держится во всех версиях ([текст формата](../spec/format/README.md), раздел 26). Навыки и ID через переход он не сверяет: граф держит ревью `modules`, и пока формат v0, сверки навыков через переход нет (architecture 3.7 spec). Читать у пакета прошлой версии формата опись, `languages` паспорта, ключи `skills`, `retired_skills` с их `replaced_by` и ключи задач, уроков, ловушек и приёмов по местам, которые формат держит во всех версиях, `module-kit` предложил `spec` — В15; ответит `spec` — `diff` их прочтёт (поправка 2026-11-02 к R13).
- **Команда `diff`:**

  ```
  module-kit diff [--json] (--index <module-index.json> | --first) [--published <папка пакета>]... <модуль>
  ```

  - `<модуль>` — папка модуля или папка пакета; их различает `manifest.yaml` или `inventory.json` в корне. Папку модуля `diff` проверяет и собирает, как `check` и `build`, и никуда не пишет; пакет, собранный `build`, избавляет CI от второй проверки с решателями;
  - `--index` — `module-index.json`, который CI уже сверил рецептом `release-verify`: подписей CLI не проверяет (R77 spec). Индекс он читает по местам, которые формат держит во всех версиях ([текст формата](../spec/format/README.md), раздел 26), и берёт из него все версии модуля. `--first` говорит явно, что опубликованных версий нет, как сборка индекса без прошлого (поправка 2026-11-02 к R63 spec): пропущенный файл молча не пройдёт;
  - `--published` — папки пакетов файлами ([текст формата](../spec/format/README.md), раздел 25), без `device/`. Пакет `diff` узнаёт по дайджесту байтов `inventory.json` — это дайджест пакета, — а затем сверяет `server.json` и `device.json` по описи. Лишние папки он пропускает. Нет пакета новейшей опубликованной версии — сравнить нельзя; нет других — правила (в), (д) и (е) идут по тем, что даны, а отчёт называет версии, с которыми не сравнивал;
  - код 0 — версия принята или модуль не изменился; 1 — отказ: строка на каждое нарушенное правило, `<ID>: <путь>: <сообщение>`, и нарушения проверки модуля тоже; 2 — сравнить нельзя: вызов, ввод-вывод, разорванная цепочка дайджестов, нет пакета новейшей опубликованной версии. Нет пакетов других версий — сравнение идёт, а отчёт называет версии, с которыми не сравнивал;
  - отчёт: модуль, новая версия, с какими версиями сравнено, найденная часть, допустимые следующие версии и поднятая часть. Затем изменения, по строке: часть версии, путь — JSON Pointer в каноническом виде или в списке части для устройства, — и что изменилось; у экземпляров — значения параметров. С `--json` — тот же отчёт данными;
  - в сеть CLI не ходит: индекс и пакеты кладёт CI `modules` (architecture 3.7 spec).
- **Библиотека** — одна функция над проверенными пакетами — новым и опубликованными — и индексом; CLI её обёртывает, а с этапа 4 её зовёт `module-registry` (R17 spec). Карточка называет у CLI три команды, и правку под `diff` отправляет T05 (architecture 3 spec).
- **Тесты:**
  - векторы сравнения, когда их добавит формат (В14), из `spec.Format` (R64 spec);
  - до того — свои случаи на примерах формата: по случаю на каждую строку таблицы и на каждое правило, на сопоставление экземпляров шаблона, на 0.y.z и 0.0.z, на снятую версию и на переход формата;
  - модульные тесты кодов завершения и отчёта: модуль не изменился, нет пакета новейшей версии, дан не весь набор версий — правило (д) без отказа и версии без сравнения в отчёте, — разорванная цепочка, `--first`, переход формата.

### 3.6. Библиотека и CLI

Что строит эпик кода — E2 в таблице 2 [RUN.md](../RUN.md) — и кто чем пользуется. Каждая часть исполняет свой раздел [текста формата](../spec/format/README.md) и проходит его векторы из `spec.Format` (R64 spec). Тип каждой части формата — из `types/formatv0`, открытого вида — из `types/formatv0/open` (R72 spec). Устройство пакетов Go и имена функций решают задачи эпика (R16).

- **Части библиотеки:**

  | Часть | Где задано | Векторы | Кто зовёт |
  |---|---|---|---|
  | раскладка модуля и читатель YAML | [текст формата](../spec/format/README.md), разделы 4 и 10 | `rules/yaml.*` и `rules/module.*` | проверка модуля |
  | схемы | [текст формата](../spec/format/README.md), разделы 5 и 8 | примеры `valid/` и `invalid/` | проверка модуля |
  | правила частей и ярусы | [текст формата](../spec/format/README.md), разделы 11–18 и 21 | `rules/<ID правила>/`, `tiers/` | проверка модуля, сборка пакета |
  | виды проверки, нормализация и вердикт | [текст формата](../spec/format/README.md), раздел 15 | `verdicts/` | `api`, eval-раннер `tutor`; правила задачи, которые проверка видит сама |
  | песочница Starlark | [текст формата](../spec/format/README.md), разделы 15 и 24; R11 | `verdicts/predicate/`, `rules/task.template-solver/` | условие, решатели |
  | открытый вид | [текст формата](../spec/format/README.md), раздел 6 | `open-view/` | `api`, команда `open` |
  | проверка утечки | [текст формата](../spec/format/README.md), раздел 20 | `leaks/`, `rules/task.no-leaks/`, `rules/lesson.no-leaks/` | `api` — на словах наставника, проверка модуля — на текстах автора |
  | генератор | [текст формата](../spec/format/README.md), раздел 22; R10 | `random/` | экземпляр попытки |
  | шаблоны и решатели | [текст формата](../spec/format/README.md), разделы 23 и 24 | `templates/` и правила шаблонов | проверка модуля, экземпляр попытки |
  | пакет и канонический текст | [текст формата](../spec/format/README.md), раздел 25; R09 | `packages/`, `tiers/` | сборка пакета, чтение пакета |
  | индекс модулей | [текст формата](../spec/format/README.md), раздел 26 | `indexes/` | сборка индекса, чтение индекса |
  | сравнение версий | R13 | своих векторов нет — В14 | `diff`, с этапа 4 — `module-registry` |

  Тест векторов обходит всё, что лежит в `spec.Format`, и падает на векторе, которого не знает. Пока эпик идёт, векторы частей, которых ещё нет, стоят в списке пропусков. Правило формата проходит свои векторы в той задаче, где есть часть, которой оно проверяется: например, `task.no-leaks` — с проверкой утечки, а `packages/with-solver` — с решателями. Промежуточные релизы линии 0.1 код несут, но их никто не берёт. Первый релиз, который берут другие, — первый релиз линии 0.2 — выходит, когда список пуст, и с ним тест не даёт списку вырасти (R16).
- **Что библиотека даёт потребителям** — `api`, eval-раннеру `tutor`, CLI, а с этапа 4 — `module-registry`. Ввода-вывода у неё нет: файлы ей дают байтами или как `fs.FS` (repositories 1 spec):
  - **чтение пакета** — по цепочке дайджестов от проверенного индекса: индекс → опись → части → файлы (R62 spec, R63 spec). Подписей библиотека не проверяет (R77 spec);
  - **версия модуля для новой попытки** — новейшая по semver неснятая версия в окне формата, по индексу. Это вопрос `api` (architecture 3.3 api): правило одно, и держит его библиотека, как держит semver `diff` (R13);
  - **экземпляр попытки** — номер `below(count)` места зерна и задача с подставленными числами экземпляра, без выражений и Starlark (раздел 3.3; R60 spec);
  - **открытый вид** — паспорта, графа навыков, каталога приёмов, шагов решения, урока, задачи и экземпляра, по пометкам `x-open` (R05 spec; R45 spec);
  - **вердикт** — ячейки и пункта по прочитанным значениям ячеек, с причиной у «не прочитать» и ловушкой у неверного значения. Условие считает песочница, с `context` вызывающего (раздел 3.4). Тип наблюдения придёт с контрактами — раздел 2.6;
  - **проверка утечки** — ключи и фразы-утечки задачи, которые нашлись в тексте (R57 spec);
  - **проверка модуля, сборка пакета, сборка индекса и сравнение версий** — для CLI, а с этапа 4 и для `module-registry` (R17 spec).
- **Команды CLI.** У всех один смысл кода завершения: 0 — принято, 1 — отказ по правилам формата, с ID каждого нарушенного правила, 2 — команда не смогла сделать своё: вызов, ввод-вывод, разорванная цепочка дайджестов. Чего нет — прошлого индекса, снятий, — команда слышит явно, а не по пропущенному файлу. В сеть CLI не ходит (architecture 3.7 spec).

  | Команда | Что читает | Что пишет | Кто зовёт |
  |---|---|---|---|
  | `check <модуль>` | папку модуля | отчёт: нарушения с ID правил и предупреждения — о картинке с прозрачными пикселями (вторая поправка 2026-11-01 к R51 spec) | CI `modules` |
  | `build <модуль> <папка>` | папку модуля, которая прошла проверку | пакет файлами: `inventory.json`, `server.json`, `device.json` и `device/`. Архив для релиза кладёт рецепт `modules` (R03 modules) | CI и релиз `modules` |
  | `index` | прошлый индекс или явное «прошлого нет», папки пакетов релиза, его тег и снятия — файл `withdrawals.yaml` по форме, которую принесёт T67 `spec`, или явное «снятий нет» | `module-index.json` — канонический текст индекса; отказ — с ID правила индекса | рецепт `release-files` `modules`, внутри общего релиза (R63 spec) |
  | `diff` | модуль или пакет, проверенный индекс или `--first`, пакеты опубликованных версий | найденная часть версии и изменения (раздел 3.5) | CI `modules` |
  | `open` | индекс релиза `modules`, индекс новейшего релиза — ради отметок о снятии, — пакеты | файл открытых видов и медиафайлы (ниже) | CI `canvas`, для страницы образцов |
  | `--version` | — | версию релиза | все |
- **Команда `open`** (R15). Сборка страницы образцов берёт задачи и медиафайлы из релиза `modules` через CLI `module-kit` (R25 spec):

  ```
  module-kit open --index <module-index.json релиза> --latest <module-index.json новейшего релиза> --packages <папка пакетов> --out <папка>
  ```

  - **Входы.** Оба индекса CI `canvas` уже сверил рецептом `release-verify` (R77 spec), а пакеты скачал по их записям (вторая поправка 2026-11-02 к R63 spec). Индекс релиза называет версии, а отметки о снятии команда читает в индексе новейшего релиза: только он знает обо всех снятиях (поправка 2026-10-28 к R25 spec). Пакет команда узнаёт по дайджесту байтов `inventory.json` и сверяет по цепочке, а у медиафайлов — `device/` — каждый файл по списку части для устройства.
  - **Какие версии.** У каждого модуля — новейшая по semver версия в окне формата, которую новейший индекс не отметил снятой: правило — то же, что у новой попытки в `api`. Пропущенные снятые версии называет вывод.
  - **Вывод:**
    - файл `open-views.json`, как `tutor-open-tasks` v0 (R64 tutor): `format`, `version`, а дальше модули. У модуля — ID, версия, `module_format_version` и дайджест пакета, открытый вид паспорта, `open.Manifest`, — `canvas.digit_height` канва берёт из него, — и открытые виды задач, `open.Task`, по порядку ID. Пишет его функция канонического текста (раздел 3.2);
    - медиафайлы задач — в `media/<ID модуля>/<версия>/<путь>`, а рядом — `LICENSE` и `NOTICE` той же версии, побайтно, только сверенные: часть для устройства несёт их к каждому, кто получает содержание ([текст формата](../spec/format/README.md), раздел 10).
  - **Что решит протокол eval:** какие экземпляры шаблона отдаёт команда — `canvas` просит экземпляр по зерну (architecture 3.5 canvas) — и как считается дайджест открытого вида каждой задачи (В67 `tutor`). Это раздел 2.5, «Отложено», и В17. Строится команда после протокола, так что временного поведения у неё нет.
  - **Когда.** Страница образцов ждёт протокола eval — эпика E3 `spec`, — и E5 `canvas`. Первому приложению она не нужна (COORDINATION.md `spec`). Поэтому `open` строится после протокола, вне первого релиза (R16).
- **Что решают задачи эпика кода** — каждое с вариантами, лицензией и точной версией (RULES.md, Licenses; Exact versions only):
  - чем читать YAML 1.2.2 по правилам раздела 4 [текста формата](../spec/format/README.md). Вторая реализация `spec` берёт пакет npm `yaml` 2.9.1 и проверяет правила по его дереву;
  - чем проверять JSON Schema 2020-12 и собирать аннотации `x-open` для открытого вида: отметка считается только там, где её подсхема проходит ([текст формата](../spec/format/README.md), раздел 6). Вторая реализация `spec` берёт `ajv` 8.20.0;
  - нормализация Unicode: NFKC, простая строчная буква и White_Space ([текст формата](../spec/format/README.md), раздел 15). Таблицы `unicode` в Go 1.27.3 — Unicode 17.0.0 (`const Version` в `src/unicode/tables.go`, прочитано 2026-11-02), а NFKC в стандартной библиотеке нет. Какую версию Unicode называет релиз, решает задача вердикта: формат велит её назвать ([текст формата](../spec/format/README.md), раздел 15);
  - тип наблюдения — когда придёт контракт E3 `spec` (раздел 2.6).

## 4. Источники

Внешний факт — условия поставщика, цена, закон, документация библиотеки — встаёт сюда с источником и датой прочтения (RULES.md, The bar).

- **Песочница решателей standalone** (раздел 3.4) — [mathtrail/mathtrail-standalone, `SPEC.md`](https://github.com/mathtrail/mathtrail-standalone/blob/c6cbeb2/SPEC.md), раздел 6 «The Starlark solver», ветка `main`, коммит c6cbeb2, прочитано 2026-10-19:
  - 6.1: «the program is written by the same model that wrote the task»;
  - 6.4, рекурсия выключена: «A recursive Starlark function recurses on the Go stack, and a stack overflow in Go cannot be recovered: it would take the whole instance down, not the request»;
  - 6.5: «Every helper that builds a list is capped at 1,000,000 elements», «a step for every sixteen bytes»; «There is no random number generator, seeded or otherwise. A brute force that samples proves nothing about uniqueness, and a verdict that depends on a seed is a verdict nobody can reproduce from the task alone»;
