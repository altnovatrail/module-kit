## 1. Purpose and bounds

**Does** — by the card, architecture 3.7 spec:
- holds the semantics of the module format — one library for all consumers. The verdict and the check of keys at publication depend on one code of the check kinds (R17 spec). Through updates, R03 spec is held by the format's test vectors — `format/vectors/` of `spec`: CI of `spec` passes them with its second implementation, and CI of `module-kit` passes them all (R42 spec; repositories 3 spec);
- reads an author's module — YAML 1.2.2 with the format's constraints — and checks it against JSON Schema 2020-12 and the format rules. A refusal names the rule's ID (R45 spec). What is checked, the card lists:
  - the schema, the skill graph without cycles, the references, the anchor skills of the shared taxonomy and the manifest's dependencies (R49 spec, R50 spec);
  - the tasks, the slot checks, the trap and technique catalogs, the lessons (R51 spec, R56 spec, R57 spec, R58 spec);
  - the templates with all their instances and their solvers (R60 spec, R61 spec);
  - the author's texts that the learner sees before solving — by the leak check (concepts 10 spec; R57 spec).

  Of a picture with transparent pixels the CLI warns but does not refuse (the second 2026-11-01 amendment to R51 spec). Of a number in a text of the whole module — a rung template, a trap advice, a technique, a solving step — it also warns but does not refuse ([format text](../spec/format/README.md), section 20; the 2026-11-08 amendment to R57 spec) (R50, R52). With format 0.4 the check also holds the page of a workbook — the layout by `page.yaml` and the rules `task.workbook-page` and `lesson.workbook-page` —, a worked example on a workbook with `lesson.example-fills`, the kind `time`, the flag `notation: word` of a choice written by hand, the picture paths of a template with placeholders, the leading question and the description of a step in the leak check, the numbered list of a lesson and the rule `yaml.printable` ([format text](../spec/format/README.md), sections 2, 4, 14, 15, 18, 20, 21 and 23; R52);
- reads the module format versions in the window. While the format is v0, the window holds only the current version, 0.4, and a module of 0.3 and older is rejected (R17; R52). A module is checked, built and executed by the version that its manifest names, and a module outside the window is rejected with a reason (R44 spec);
- builds the module package and the module index (R17 spec):
  - the package — the canonical view with the tier of each skill and the numbers of each instance of a template, the device part and the inventory (R62 spec);
  - the index — from the previous release's index, with an entry of each published version by its package digest and with the marks of withdrawal (R63 spec).

  The package is a signed, content-addressed version of a module, and the index is a signed cumulative list of the published versions (concepts 15 spec). At a release of `modules` they are built by the CLI of `module-kit` (repositories 4 spec);
- compares a new version of a module with each published one, withdrawn ones too, by the format's rules of version comparison, and checks retired skills: a withdrawal does not free the skills' IDs ([format text](../spec/format/README.md), section 27; concepts 3 spec; R89 spec). A package of a previous format version it reads by the places that the format keeps in all versions, and across a format transition it checks the skills and the IDs the same way ([format text](../spec/format/README.md), section 2). The version part the comparison finds itself, and the CLI has a command of its own for it, `diff` (R13; section 3.5);
- fills task templates (concepts 9.3 spec; R60 spec):
  - goes through the combinations of parameters — no more than 10,000 per template — and builds the instances;
  - the key of each instance is computed by the solver already when the module is checked (R61 spec);
  - the instance of an attempt is picked by the generator from the attempt's seed (R59 spec; section 3.3);
- builds the open view of a task — without the key, the solution and the traps — by the marks `x-open` in the format's schemas: a field without a mark is closed (architecture 1 spec; R05 spec; R45 spec). It builds the open views on the server from the server part, and they are not part of the package (R62 spec);
- holds the check kinds and normalization: in format v0 these are `number`, `fraction`, `choice`, `predicate` and `rubric` (concepts 9.2 spec; R56 spec). This is the platform's code, shared by all modules: a module only chooses the kind and sets its parameters (R02 spec);
- gives the verdict: compares the observation with the key or the predicate (architecture 1 spec; concepts 9.1 spec; R03 spec). A verdict is admitted only if the key or the predicate was given by the author, a solver or an adult, and with a key that AI derived there is no verdict (concepts 9.4 spec; R04 spec);
- joins the observations of two readers into one, by the slot check, and gives the verdict by the joined observation as a whole, with the causes of "unreadable" from the observation (R86 spec; [contracts text](../spec/contracts/README.md), section 10). With the same code it gives the eval runner of `tutor` the verdict by the truth of a sample's markup (R95 spec);
- holds the leak check — the search for the key and the leak phrases that the author named (concepts 10 spec; R57 spec). `api` checks the tutor's text with it before the text goes to the device (architecture 3.5 spec), and the module check checks the author's texts (concepts 10 spec);
- executes Starlark in a sandbox, as in standalone (repositories 7 spec), — in go.starlark.net of the version that the format names, and in one dialect for all the Starlark of the format (R88 spec):
  - check predicates — a count of steps that reaches 1,000,000, or an error, gives "unchecked" (R56 spec; R88 spec);
  - template solvers — no more than 100,000,000 steps for all the instances of a template (R61 spec).

  The clock, concurrent runs and the version of the interpreter — section 3.4;
- checks a package by the chain of digests from the index that a pull request of `api` pinned: index → inventory → parts → files (R62 spec, R63 spec). The library checks no signatures: the signature of a release file is checked by `spec`'s recipe `release-verify` where the file enters NovaTrail (R77 spec; the 2026-11-01 amendment to R17 spec);
- gives the author a CLI: check a module, build a package, build the index and compare versions — `diff` (R13; section 3.5) —, and to the build of the samples page of `canvas` it gives the open views and the media files by the command `open`: for a template, the instance by the seed, and for each task, the digest of its open view (R15; R93 spec). The commands — section 3.6. The CLI builds the index inside the shared release of `modules`, after the number and before publication (architecture 3.7 spec; R63 spec). "Build" writes the package as files, and the package's archive for the release is put by a recipe of `modules` (R03 modules). The withdrawals "build the index" reads from the file `withdrawals.yaml` of `modules` — by `$defs/withdrawals` of the index's schema ([format text](../spec/format/README.md), section 26).

**Does not:**
- does not call AI (architecture 3.7 spec). The work is read by `tutor`, and `module-kit` already gets an observation from `api` (architecture 1 spec; architecture 3.5 spec);
- does not go to the network: the library is computation without input or output, and the CLI only reads and writes the module's files (architecture 3.7 spec; repositories 1 spec). The build gets the previous index as a file: the shared release of `.github` downloads and checks it (the 2026-11-02 amendment to R63 spec);
- stores no learners' data (architecture 3.7 spec): of the platform's parts, only `api` stores them on the server (architecture 1 spec; R15 spec);
- does not own the format. The schemas, the format text, the examples and the test vectors lie in `format/` of `spec` (R42 spec; R45 spec; repositories 5 spec), and `module-kit` holds the format's semantics in code (R17 spec). CI of `spec` checks the examples with a JSON Schema validator, and the vectors with its second implementation, without `module-kit`: otherwise `spec` would depend on what depends on it (repositories 3 spec);
- does not define the random generator and the derivation of seeds. `spec` defines them, with test vectors, and `module-kit` passes them (architecture 1 spec). The generator is PCG from Go's `math/rand/v2`, and the places of randomness are derived as in standalone's simulator (R59 spec). They are one for the whole platform — for `module-kit`, the widgets, `engine` and `sim` (R27 spec);
- does not sign packages and the index and checks no signatures: the signature is put by the shared release workflow from `.github`, and checked by `spec`'s recipe `release-verify` (R17 spec; R77 spec; repositories 4 spec);
- does not choose a lesson or a task and does not compute the learner model: that is `engine` and `learner-model` (architecture 1 spec). Their types of the graph are simple and not from `module-kit`: `learner-model` defines them, and `engine` takes them from it (architecture 3.8 spec; R28 spec);
- does not publish modules: the registry v0 is the signed index that CI of `modules` builds. The registry service will appear at stage 4 and will also be built on `module-kit` (R17 spec).

**Data and links:**
- it has no data of its own: it works with the module, the package and the index that it is given. There are no learners' data and no secrets, as in no repository (architecture 3.7 spec; RULES.md, Hard rules). In the process of `api` it gets the observation and the key or the predicate of a task, and returns the verdict (architecture 3.5 spec);
- at build it depends on nothing but `spec` (repositories 2.1 spec; repositories 3 spec):
  - the format's schemas, examples and vectors it takes as the Go module `github.com/altnovatrail/spec` — `spec.Format` at the release tag, the same as that of the submodule `spec/` —, not from the submodule;
  - the types of the parts, of their open views, of the canonical view, of the inventory and of the index — from the packages `types/formatv0` and `types/formatv0/open` of the same module (R64 spec, R72 spec);
  - the observation — the contract package `novatrail.observation.v1` of the nested Go module `github.com/altnovatrail/spec/contracts`, which `spec` generates from the API contracts, and the vectors of the join and of the verdict by an observation — `contracts.Vectors` of the same module (R86 spec; the 2026-11-03 amendment to R64 spec). `tutor`, `module-kit` and `api` exchange the observation in one process, and it has one type (R83 spec). The module `contracts` requires the protobuf runtime and connect-go: these are third-party Go modules, not repositories. Since T28 the package `observation` takes the protobuf runtime, BSD-3-Clause, and `ci-licenses` sees it, while connect-go does not go into the build (R29; section 3.1).

  The version of the module `spec` in `go.mod` and the submodule are moved together, by a move to a tag, and the module `spec` is excluded from Dependabot `gomod` (R64 spec). So is the nested module `spec/contracts`: its tag `contracts/vX.Y.Z` carries the number of the tag of `spec`, and the module, the submodule and the package are moved by one move to a tag (R64 spec; R83 spec). Both modules are in `go.mod` since T19, at v0.9.2, Dependabot does not raise them, and `ci-lint` checks their versions against the submodule (R20; section 3.1);
- it is imported by `api` and the eval runner of `tutor`, and the CLI is taken at an exact tag by CI of `modules` and CI of `canvas` — as a release binary, which `release-verify` checks before the first run (repositories 1 spec; repositories 3 spec; R77 spec). CI of `canvas` takes the CLI to build the samples page: the page gets the open views and the media files at build, from the packages of the release of `modules` (R25 spec; architecture 3.2 spec). For this the CLI has a command of its own, `open` (R15; section 3.6). Later, at stage 4, `module-registry` and `module-pipeline` are built on it (architecture 3.7 spec; repositories 2.1 spec);
- `sim` does not take it: it reads the server part by the types of the canonical view from `spec` (architecture 3.9 spec; R62 spec). `learner-model` and `engine` read no packages: `api` passes them the graph (architecture 3.8 spec);
- the verdict is reproducible. An attempt keeps the digest of its package — the digest of the inventory —, the module format version, the version of `module-kit` and the seed. The verdict is repeated from the stored observation, without AI, by the release of `module-kit` that gave it (architecture 1 spec; R03 spec; R44 spec). A change of the behaviour of a check kind is a new version of the format (R44 spec);
- a new AI model is admitted by eval, and the false alarms there are counted by the verdict, through `module-kit` (architecture 4.6 spec; repositories 4 spec);
- the CI checks came even before the code: the shared checks from `.github`, among them `docs-check-repo`. Which they are and what holds the merge — R30 spec and architecture 3.11 spec. T17 of `spec` connected them, and its session wrote the CI files here; the CI files for its own code are written by this repository's session (the 2026-10-21 amendment to R30 spec).
  - The findings of CodeQL, Scorecard and SonarCloud are closed before a new task (rule 12 of [RUN.md](../RUN.md)), and the reasons, shared by all repositories, of those that stay open are recorded in R33 spec.
  - The Go checks came with the skeleton of the CLI (R04): their recipes are their own, and they are run by the Go wrapper — the shared `go.yml` of `.github`, which was tested on that skeleton (R16 .github). CodeQL reads Go since T12: the shared `codeql.yml` of `.github` v0.1.3 builds it with Go from the stage `toolchain` (R06). The TypeScript wrapper is tested on the first TypeScript code, in `canvas` (repositories 6 spec; architecture 3.11 spec).
  - The release is put out by the shared `release.yml` of `.github`, and the files for it are built by a recipe of its own, `release-files` (R07; section 3.1).
  - Code comes with its tests. Since T18 the coverage of the tests goes to Codecov, and the merge waits for `codecov/patch` — at least 90% of the changed lines —, once the author puts it in the ruleset `main` (RULES.md, How we work; R48 spec; R18; section 3.1);
- stage 1, together with `modules`: the module format is tried at once on three modules of two subjects (repositories 6 spec; R08 spec; R41 spec; product 11 spec). The work in the order of repositories 6 spec is led by the cross-repository plan — COORDINATION.md of `spec`. There the rows 3.1 and 3.2 of `module-kit` are closed — the move to the line 0.6 and the detailing —, and 3.3, the code epic, E2, is open (R76 spec).

### 2.1. The module package and the canonical text

- **Gist:** how `module-kit` builds the module package by R62 spec and what it writes its canonical text with. The contents of the package were decided by the format, and what was decided here is how to carry them out.
- **Decided** (R09): the canonical text is written by a function of its own, which stops on a value outside the format, and the canonical view is built from the JSON value of each file as it is. How the package is built — section 3.2.
- **Task:** T01.

### 2.2. The generator in CI

- **Gist:** what `module-kit` executes the generator and the places of randomness with by R59 spec — Go's standard library or its own code — and how its CI passes the vectors `format/vectors/random/` of `spec`.
- **Decided** (R10): the generator is its own code by the constants of the [format text](../spec/format/README.md), section 22, with an error on an argument outside the domain, and `math/rand/v2` and `hash/fnv` are only the reference in the tests. The generator lies in `internal/`, and what goes outside is the choice of an attempt's instance. How it is built — section 3.3.
- **Task:** T02.

### 2.3. The clock, concurrent runs and memory of Starlark

- **Gist:** how much time the evaluation of a check predicate and a template solver have, how many of them run at once, who holds the clock and the slots, what a clock that fired means, how much memory the sandbox has and whether a separate process is needed. The steps, the dialect and the solver's place were decided by the format, and the clock and concurrent runs it left to `module-kit` (architecture 3.7 spec).
- **Decided** (R11): go.starlark.net — of the version that the format names: since 0.3 it is 4f4267fb140d, and the dialect, one for all the Starlark of the format, the predicate's too, the format names itself (R88 spec; R17). The clock is a safeguard of `module-kit`: 1 s for a predicate and 60 s for a template solver. The library holds no slots: concurrency is the caller's, in `api` no more than `GOMAXPROCS` at once (architecture 3.7 spec). How it is built — section 3.4.
- **Put off:** the memory of third-party Starlark. From stage 4 the predicates in `api` and the solvers in `module-registry` are written by third-party authors too, and go.starlark.net does not count memory. `spec` answered В12 by an addition to О-9: from stage 4 the Starlark of a third-party module is executed in a separate process with a memory limit, and how is decided by the tasks of `api` and `module-registry` (architecture 3.5 and 3.13 spec). Until then — Д10 in table 4 of [RUN.md](../RUN.md).
- **Task:** T03.

### 2.4. The semver rules for `diff`

- **Gist:** by what rules `module-kit` compares a new version of a module with the previous one: what raises the major, the minor and the patch version, what the comparison finds itself, and what the author declares. Since v0.6.4 the card names the comparison among the points of "To decide when detailed": a new version is compared with each published one below it by semver, withdrawn ones too (architecture 3.7 spec; R12). Before that only the task that set up this repository named it (T05 `spec`). The card has no command `diff`: the CLI there is "check, build, build the index". Whether it is a separate command or part of the check, the task decides.
- **Decided** (R13): the comparison itself finds the lowest version part, and the author may raise a higher one, but not a lower one. Major — when something of what the learner had in the previous version is gone or means something else. Packages are compared, and the CLI has a command of its own for the comparison, `diff` — section 3.5. The table "change — version part", the rules of comparison and with which versions to compare, format 0.3 took to itself — below.
- **spec's answer:** to В14 and В15 — format 0.3 (R89 spec; R101 spec; R17). The principle of the parts, the table "change — version part", the rule of 0.y.z and the rules of comparison are now in the [format text](../spec/format/README.md), section 27, with the vectors `vectors/versions/`, and the IDs of the rules are `module-version.*`. A new version is compared with each published one, and a package of a previous format version is read by the places that the format keeps in all versions ([format text](../spec/format/README.md), section 2). Where the answer differs from R13 — section 3.5.
- **Task:** T04.

### 2.5. A CLI command for open views

- **Gist:** whether the CLI of `module-kit` needs a command of its own that gives the open views of tasks to the build of the samples page of `canvas`, or whether the card's commands are enough for that build — check, build, build the index (architecture 3.7 spec). R25 spec left the question to the detailing of `module-kit`, and the 2026-10-28 amendment to R25 spec left it there too. It is decided here: the CLI is part of `module-kit` (R17 spec). A new command changes the card, and the result of the detailing sends the edit of the card as a row of table 3 «в реестр spec» (section 2).
- **Decided** (R15): a command of its own, `open`, at a release of `modules`. It writes the file of open views — for each module, by its newest unwithdrawn version, the ID, the version, the package digest, the open views of the manifest and of the tasks, as in `tutor-open-tasks`, — and the media files of the tasks, `LICENSE` and `NOTICE`, checked against the inventory. Withdrawn versions it skips. It is built by the last task of the code epic, after the first release (the 2026-11-04 amendment to R16). How it is built — section 3.6.
- **spec's answer:** what `open` gives for a template and how the digest of an open view is computed, the eval protocol decided — the answer to В17 (R93 spec; R17). For a template — the instance by the seed, and the digest of an open view is `sha256:` and the SHA-256 of its canonical text, for an instance — with the numbers substituted.
- **Task:** T05; the command was built by T40 (R43).

### 2.6. The type of the observation

- **Gist:** `module-kit` gives the verdict by the observation — what `tutor` read in the work (architecture 3.5 spec). `tutor`, `module-kit` and `api` exchange the observation in one process, and it has one type — code that `spec` generates from the contracts into the nested Go module `spec/contracts` (R83 spec).
- **spec's answer:** the contract of the observation came with the epic E3 of `spec` — the package `novatrail.observation.v1` of the module `spec/contracts` (R86 spec; R17). `module-kit` joins two readings into one, by the slot check, and gives the verdict by the joined observation; how, the [contracts text](../spec/contracts/README.md), section 10, says, and the vectors are `contracts.Vectors`. The module format does not change from this: the verdict by the read value stays by the [format text](../spec/format/README.md), section 15.
- **Decided** (R29): the package `observation` over `verdict` — `Validate`, `Join`, `Verdicts` and `Essay`. An invalid observation is the error `ErrNotValid`, so `unchecked` in a verdict by a valid observation is the `unchecked` of a predicate. `verdict` stays without protobuf. How it is built — section 3.6.

### 3.2. The module package

The CLI builds the package at a release of `modules`, from the module's folder, by the format version that its manifest names ([format text](../spec/format/README.md), section 25; R62 spec). A package is built only from a module that has passed the check: the schema and all the format rules (R45 spec). The code came with T33 (R34): `modulepackage.Build(ctx, fsys)` first checks the module with `module.Check` and rejects a module with breaches by a `*Refusal` with the report, and returns the package as the bytes of its files, `Package.Files` — the CLI writes them to disk, T37; `modulepackage.Read(fsys, digest)` reads a package as files by the chain of digests; the canonical text is `internal/canonical.Text`.

- **The parts of the package** (concepts 15 spec):
  - the server part is the canonical view, `server.json`: the module as one JSON object, with all its content, and with the keys, the solutions and the traps too;
  - the device part is `LICENSE`, `NOTICE` and the media files, and, once the format has widgets, their bundles. It is named by its listing, `device.json`;
  - the inventory is `inventory.json`: the format version, the module's ID and version, and both parts by their digests and sizes. It is not the module manifest, although in code and schemas the manifest is called `manifest`.
- **How it is built:**
  1. The YAML reader gives the JSON value of each file of a part (R45 spec). Files and folders whose names begin with `.`, comments and `eval/` do not go into the package.
  2. The canonical view: the parts of the module are under members of their own, `manifest`, `skill_graph`, `traps`, `techniques` and `solving_steps`, and `tasks` and `lessons` as objects by local ID. The value of a part is the JSON value of its file as it is: a template as it is written, and no default values (R09). Beyond the parts, there are `skill_tiers`, the tier of each skill, by the [format text](../spec/format/README.md), section 12, when the module has a skill graph, and `instances`, the numbers and the solver's results of each instance of a template, by the [format text](../spec/format/README.md), sections 23 and 24, when any of the tasks are templates. A member without its part — `skill_tiers` without a skill graph, and `instances` without templates — is absent from the view. An integer that the YAML reader gave as a double — `50.0` or `5e1` — goes into the view as the integer `50` ([format text](../spec/format/README.md), section 25).
  3. The listing of the device part is an object: `license` — the digest and size of `LICENSE`; `notice` — of `NOTICE`, only if it exists; `media` — of each file of `media/` by its path from `media/`, only if there are such files (`inventory.schema.json`, `$defs/device_listing`).
  4. The inventory: `module_format_version`, `id` and `version` as in the manifest, and `server_part` and `device_part` — the digest and size of the canonical text of the canonical view and of the listing.
  5. The package digest is the digest of the canonical text of the inventory. A package as files is a folder: `inventory.json`, `server.json` and `device.json` — the canonical texts of the inventory, the canonical view and the listing — and `device/` with `LICENSE`, `NOTICE` and `media/<path>` byte for byte. So "build" writes them, and the package's archive for the release is put by a recipe of `modules` (R03 modules; architecture 3.7 spec).

  The package depends only on the module's files and the format version of its manifest: it holds no version of `module-kit`, no time and no paths (R62 spec).
- **The canonical text** is written by a function of its own over a tree of JSON values — object, array, string, integer, `true`, `false`, `null` (R09):
  - the members of an object go in the order of the UTF-16 code units of their names, and there is no whitespace between tokens;
  - an integer is written in decimal digits, a negative one with the sign `-`;
  - in a string only `"` and `\`, `\b`, `\t`, `\n`, `\f` and `\r` are escaped, and the other characters up to U+001F are written as `\u00` and two lowercase hexadecimal digits. `<`, `>`, `&`, U+2028 and U+2029 are written as they are, and characters are not normalized;
  - the text is UTF-8, with no BOM and no newline at the end;
  - on a number with a fractional part, an integer outside ±(2^53−1), a string that is not valid UTF-8 and a value that is not JSON, the function stops with an error. On a checked module such a refusal means a defect in the code of `module-kit` (R09). Only it writes the texts of the package and of the module index: not `encoding/json`, not `jsontext` and not a walk over the types of `formatv0`.
- **A digest** is `sha256:` and 64 lowercase hexadecimal digits of the bytes, and a size is the number of the bytes (concepts 15 spec). The attempt keeps the package digest (architecture 1 spec).
- **Reading a package** goes by the chain of digests from the package digest that the index pinned: inventory → parts → files. The library checks no signatures (R62 spec, R63 spec, R77 spec). Beyond the digests, `Read` holds the format version of the inventory, the schema and the canonical text of each of the three texts, and that the manifest of the view names the module of the inventory; a refusal is `ErrChain`, `ErrFormatVersion` or `ErrNotCanonical`, with the file's path (R34). JSON is read by `canonical.Parse`, shared with the index: a text not in UTF-8 and a number outside double are not JSON, `ErrNotCanonical`. Before T34 a number such as `1e700` in the inventory crashed `Read` with a panic of the schema validator (R35). `ReadParts` is the same reading without the files of `device/`: so version comparison reads a published package, which CI of `modules` gives without the device part, and compares that part by its listing (R36).
- **Who reads the package:**
  - through `module-kit`: `api`, by the digest, and the eval runner of `tutor`, and from stage 4 `module-registry` (architecture 3.10 spec; R17 spec);
  - through the CLI of `module-kit`: CI of `canvas`, for the samples page (R25 spec);
  - without `module-kit`: `sim`, by the types of the canonical view from `spec` (architecture 3.9 spec);
  - the device part is served by `api` (architecture 3.10 spec).
- **Where it lies:** at stage 1 the packages and the index lie in the releases of `modules`; at stage 2 the packages lie in the image of `api` too. To repeat a verdict, old versions of packages are taken from the releases of `modules` (architecture 3.10 spec; Т-17).
- **Tests:**
  - all the vectors of `format/vectors/packages/` and `format/vectors/tiers/` from `spec.Format` (R64 spec). CI computes the solver's results of the vector `with-solver` by a run of its own (Д44 in table 4 of RUN.md of `spec`);

### 3.3. The generator and the places of randomness

`module-kit` executes the generator and the places of randomness by the [format text](../spec/format/README.md), section 22 (R59 spec), with its own code (R10). The code came with T30 (R31).

- **The Go package** is `internal/random`: it is not part of the library's API, and other Go modules do not import it. The generator is one for the platform by its algorithm, not by its code: `engine`, `sim` and the widgets execute it themselves and pass the same vectors (R27 spec; R59 spec).
- **The package's API** (R31): `New(high, low)` — a stream from two words; `Words(seed, names)` — the words of a place, and `Place(seed, names...)` — its stream; `Stream` has `Integer`, `Below`, `Between`, `Fraction` and `Permutation`, one function of the format per method, and `MaxPermutation` is 2^31 − 1. A refusal of a function and of a place is `ErrDomain`, with a message saying what is wrong.
- **A stream** is two words of state, high and low, taken as they are. A step is `state · M + C mod 2^128` through `bits.Mul64` and `bits.Add64`, the output is DXSM, and the constants are the numbers from the format text. There is no shared state: a stream lives within one call.
- **A place of randomness** is a seed, an unsigned integer of 64 bits, and a list of names. Its stream is started by two words: FNV-1a 64 of the UTF-8 text "the seed in decimal digits, then `|` and the name, for each name", and the seed itself. There is at least one name, and a name is a non-empty string of valid UTF-8 without `|`; otherwise the place is not built, and an error is returned. In the same way, on `math/rand/v2` and `hash/fnv`, standalone's simulator derives the stream `seeded` — the place of the master seed with the names "experiment, unit, purpose" —, while the production code of standalone has no generator from a seed (R59 spec; sources 1.5 and 1.6).
- **The functions** are five, those that the vectors check. Each draws as many integers as the format text says:

  | Function | Domain | How it computes |
  |---|---|---|
  | `integer` | — | the next integer of the stream |
  | `below(b)` | b from 1 to 2^64 − 1 | a power of two by a mask; otherwise Lemire's method: the high word of the product of the integer and b, with rejection while the low word is less than (2^64 − b) mod b |
  | `between(a, c)` | a ≤ c and c − a + 1 ≤ 2^63 − 1. First a ≤ c is checked, and then, without overflow, that `uint64(c) − uint64(a)` is at most 2^63 − 2 | a + `below(c − a + 1)` |
  | `fraction` | — | the low 53 bits of the next integer, divided by 2^53 |
  | `permutation(n)` | n from 0 to 2^31 − 1 | from 0, 1, …, n − 1 in order, and for i from n − 1 down to 1, a swap of the places i and `below(i + 1)` |

  On an argument outside its domain a function returns an error and draws no integers. There is no shuffle of a list: it has no vectors, and `module-kit` shuffles nothing (R10).
- **The instance of an attempt** is one function of the templates API, `template.AttemptInstance(seed, task, count)` (R31): the number `below(count)` of the place of the attempt's seed with the names `template`, the task's ID and `instance`, for count from 1 to 10,000, `template.MaxInstances` (R60 spec; [format text](../spec/format/README.md), section 23). The number counts from 0, in the order of the counter, and count is the number of instances whose numbers the package carries: the function takes no template and counts no instances. A count outside the domain and an ID that is not a name of a place give `template.ErrDomain`. No other call is made on this place, and a module has no other places in format v0. A task's ID is lowercase Latin letters, digits and `-` (`common.schema.json`), and a place's name from it is always allowed. `api` draws the attempt's seed from a cryptographic source, and `module-kit` gets it as a number. Neither the seed nor the words of the place go to the device: the words show the seed ([format text](../spec/format/README.md), section 22).
- **What the code does not have:** randomness not from a seed — neither `math/rand`, nor the top-level functions of `math/rand/v2`, nor `crypto/rand`. `math/rand/v2` and `hash/fnv` are only in the tests.
- **Tests:**
  - all the vectors of `format/vectors/random/` from `spec.Format` (R64 spec). A vector is read by the YAML reader and the schema validator of the module check — against `random-vector.schema.json` — and by the type `formatv0.RandomVector` (R72 spec), and the numbers written as strings are parsed by `strconv`. When a seed and names are given, the derived words are compared with `state`. Then the calls go in order, and each value is compared, `fraction` as a double. The test fails if there are no vectors and if a call has no known field;
  - the place of a template is checked by the vectors of `format/vectors/templates/` too: for each seed they name the instance. The instance number of the 16 seeds of the five vectors without a solver is held by `TestAttemptInstanceOfTheVectors` in `template`, together with `Instances` at that number giving the parameters of the attempt, and the vectors as a whole are passed by the vector test (R32);
  - unit tests: each refusal and the number of integers that each function draws: `below(1)` and `between(a, a)` draw one, `permutation(0)` and `permutation(1)` none (`TestWords`, `TestDraws`, `TestRefusals`, `TestEdges`);
  - the comparison with the standard library: the stream, the functions and the words of a place are compared with `math/rand/v2` and `hash/fnv`, and the state of the stream after each function with `PCG.MarshalBinary`. An ordinary test, `TestReference`, runs on every `go test` — on the words of all the vectors, on the bounds 1, powers of two, 2^63 − 1, 2^63 + 1 and 2^64 − 1, and on 5,000 inputs from the generator itself with a constant seed. A fuzz test, `FuzzReference`, compares the same on any inputs, with permutations of up to 1024 numbers, and the same inputs, except the inputs from the generator, lie in its corpus. The reference lives only in the tests, and they need no build tag (R10).

### 3.4. The Starlark sandbox

The Starlark of the format — check predicates, template expressions and solvers — `module-kit` executes in go.starlark.net, in the caller's process (R11). The code is the package `internal/sandbox` (R28, R33).

- **Limits:**

  | Limit | What it holds | Who holds it | Where the number comes from |
  |---|---|---|---|
  | a predicate — no longer than 1000 characters | the size of the expression | the module check, by the schema | the format (R56 spec) |
  | a predicate — the count of steps does not reach 1,000,000 | the steps of one evaluation in the count of the pinned version of go.starlark.net | `Thread.SetMaxExecutionSteps`: the count reached the limit — "unchecked" | the format (R56 spec; R88 spec) |
  | the clock of a predicate — 1 s | the time of an evaluation whose steps call heavy built-in functions | `module-kit`, a constant of the release; when it fires — "unchecked" | the measurement of 2026-11-02: a simple predicate spends 6 ms on 1,000,000 steps (R11) |
  | a template expression — no longer than 1000 characters, no more steps than tokens; combinations — no more than 10,000 per template | the cost of the brute force over the instances | the module check: the length — by the schema, the combinations — by the rule `task.template-instances`; an expression has no limit of steps and no clock (R32) | the format (R60 spec) |
  | a solver — no longer than 8192 characters | the size of the program | the module check, by the schema | the format (R61 spec) |
  | a solver — the count of steps does not reach 100,000,000 per template | the steps of the top level and of all the calls of `solve` in the same count | `Thread.SetMaxExecutionSteps` on the one thread of the template: the count reached the limit — a breach of `task.template-solver` | the format (R61 spec; R88 spec) |
  | the clock of a solver — 60 s per template | the time of a program whose steps call heavy built-in functions | `module-kit`, a constant of the release; when it fires — a breach of `task.template-solver` | the measurement of 2026-11-02: a simple loop spends 0.45 s on 100,000,000 steps (R11) |
  | recursion is off | the Go stack from the recursion of Starlark functions: its overflow crashes the whole process | the dialect, `Recursion: false`; go.starlark.net catches recursion through `lambda` too. Built-in functions on deeply nested values this does not hold — they, like memory, are held only by a separate process | the format: for a solver — R61 spec, for a predicate — R88 spec |
  | concurrent runs | the CPU of the process and the wall time of the clock | the caller: `api` — no more than `GOMAXPROCS` at once, the CLI — a solver per CPU | R11; for `api` — architecture 3.7 spec |
  | a panic of the interpreter | the caller's process | `module-kit`, `recover`: "unchecked" or a breach of `task.template-solver` | R11; #672 of go.starlark.net |
  | memory | the caller's process | until stage 4 — nobody: go.starlark.net does not count it. From stage 4 the Starlark of a third-party module — in a separate process with a memory limit at the caller | Д10; О-9 |
  | the version of go.starlark.net | the count of steps and the behaviour of the language | the format names it — 4f4267fb140d —, and `module-kit` pins it in `go.mod` and excludes it from Dependabot `gomod` | the format (R88 spec); R11 |

  The steps are counted by go.starlark.net of the version that `module-kit` pinned: since 2026-10-05 the counter grows by 10 per backward jump or call, and before that it grew by 1 per instruction (sources 4.2). The same module on the same values makes the same steps on any machine, but not in another version of the interpreter: so the format names the version, and its change is a major version of the format. The limit fires when the count reaches it, while format 0.2 stopped an evaluation only past the limit (R88 spec; [format text](../spec/format/README.md), section 2).
- **The call.** An evaluation runs synchronously, in the caller's thread, on its own `starlark.Thread` and with the caller's `context`. The clock of `module-kit` and the cancellation of the `context` call `Thread.Cancel` with different reasons. The first gives "unchecked" or a breach of a rule, the second an error without a verdict. The interpreter sees a cancellation between instructions, and does not interrupt a built-in function: in the measurement `len(list(range(50000000)))` stopped only after the clock, having taken hundreds of mebibytes, and `str` of a deep list ran on one step much longer than the clock (R11; measurements 1.1). The clock runs by wall time, so the caller holds no more than `GOMAXPROCS` concurrent evaluations (architecture 3.7 spec). The sandbox has no slots and no shared state.
- **The dialect** is one for all the Starlark of the format, as in the [format text](../spec/format/README.md), section 24: `Set`, `While`, `TopLevelControl` and `GlobalReassign` are on, `Recursion` is off, `load` is forbidden, and the built-in names are the 33 names of `starlark.Universe` of the pinned version that the format lists. A check predicate and template expressions go in the same dialect (R88 spec; [format text](../spec/format/README.md), sections 15, 23 and 24). The sandbox holds the names by a list of its own, not by `starlark.Universe`: the caller's process may add its own to it, and the dialect does not change from this (R28).
- **The code** (R28) — `internal/sandbox`:
  - `CheckExpr(src, names...)` — an expression of the dialect that names only `names`, the names that it binds itself and the built-in names: the parsing by `syntax.FileOptions.ParseExpr` and the names by `resolve.ExprOptions` with a list of its own. An error is the line, the column and the words of go.starlark.net: `1:1: undefined: number`. With it `verdict.CheckPredicate` holds the rule `task.predicate-expression`;
  - `Eval(ctx, limits, src, env)` — the same `CheckExpr` on the names of `env`, then the parsing again and `starlark.EvalExprOptions` on its own thread, as the vectors count steps. `Limits{Steps, Clock}`, zero — no limit, and `Predicate` — 1,000,000 steps and 1 s. The stops are `ErrSteps`, `ErrClock` and `ErrPanic`, and a cancellation is the error of the `context`, wrapped; the error names the first reason, as the thread keeps the first reason of `Cancel`, and only when the interpreter stopped by it: an evaluation that ended by itself keeps its result and its error. `print` writes nothing, and the thread has no `Load`;
  - `Compile(src, names...)` — the same `CheckExpr`, and then a program of one assignment `_result = <src>`, built from the tree of the expression, where the names are predeclared: it compiles everything that `CheckExpr` takes, is as deep for the parsing of go.starlark.net as the expression itself, and makes the same steps as `Eval`. `Func.Call(ctx, limits, args...)` — `Program.Init` with the values of the names in order on its own thread, with the same limits, stops and errors as `Eval`. So the template expressions are computed on each combination without parsing again: without a limit of steps and a clock, because the steps of an expression of the subset are bounded by its length (R32);
  - `CheckProgram(src)` — a program of the dialect: the parsing with the options of the dialect, not a single `load`, and the names — a list of its own, as for `CheckExpr`. `Exec(ctx, limits, src)` — `CheckProgram`, the compilation and the top level of the program on its own thread, after which the global values are frozen, as Starlark freezes a module: so is a solver's `Program`. `Program.Call(fn, args...)` calls its function on the same thread, and `Program.Close()` ends its clock and the watching of the `context`: the steps of the top level and of all the calls are one count against one limit, and the clock is one — from `Exec` to `Close`. `Solver` — 100,000,000 steps and 60 s. The stops and errors are the same as for `Eval`; after a panic `Call` calls nothing, and after `Close` it returns `ErrClosed`. The error of a `context` that the caller made done is recognized by `ContextDone` — both the verdict of a predicate and the solver take it (R33);
  - the thread is a type of its own inside the package: the limit of steps, the clock, the watching of the `context`, `recover` and the first reason of the stop — one code for one evaluation, `Eval` and `Func.Call`, and for a program with all its calls. The thread sees a cancellation at the entry into each Starlark function, at the return of each call and at a backward jump, so a clock that fired between calls of `solve` stops the next one at its entry.
- **The address reserve.** The import of `go.starlark.net/starlark` on 64-bit linux and darwin reserves 4 GiB of address space for small integers, and if that fails, it writes to `log` and computes more slowly (sources 4.6). Every process that imports `verdict` inherits this — `api` and the eval runner of `tutor`: the reserve takes no memory, but a limit of the process's address space sees it (R28).
- **The CLI** checks template solvers one per CPU (`GOMAXPROCS`), each on its own Starlark thread, and prints the result in the order of the templates: `template.Instances` is a function for one template, and it may be called from several goroutines at once. The pool is held by the check itself (R38): `module.Check(ctx, fsys)` expands the templates of the module in `runtime.GOMAXPROCS(0)` goroutines, each takes the next template in the order of the paths, and the result takes its place by the task's path, so the report does not depend on the number of goroutines. The `context` is the caller's; in the CLI, SIGINT and SIGTERM make it done. `modulepackage.Build` takes the numbers of the instances from the check, `module.CheckModule`, and the solver runs once. Only `CheckFile`, a file on its own, runs with `context.Background()` and one at a time. The steps of a thread do not depend on its neighbours. Wall time and memory are shared by the solvers: heavy built-in functions of several templates at once reach the clock or the memory limit sooner than one at a time.
- **What is known from standalone** (sources 1.1, 1.2 and 1.3; measurements 1.1):
  - 25,000,000 steps and 2 s per run, one run per vCPU and 3 s of waiting for a slot; the limit of steps was calibrated on 450 reference solvers, and the worst needed 2,081,362 steps (R53 standalone);
  - its helpers pay a step for every 16 bytes and build no lists longer than 1,000,000 elements: so the steps bound the memory of the helpers too — 381 MiB at the ceiling of steps —, and nine tenths of the memory of a service instance are given to the Go runtime (`GOMEMLIMIT`);
  - but the memory gap is wider than one operator. The operator `*` and the repeated `xs = xs + xs` build a huge list past the counters; the literal `{}` in a loop holds 512 bytes for every nine steps, and a service instance with 1 GiB of memory was killed exactly so; the methods of the values themselves — `x.extend(range(3000000))` — take three million elements in nineteen steps (SPEC 6.6 standalone; R53 standalone);
  - standalone v1 put off a separate process, and rejected four slots with a safety clock: "Verdicts depend on the load" (R125 standalone);
  - the steps of the heaviest of its solvers on the version of standalone and on 4f4267fb140d — measurements 1.1 (R11).
- **Put off:** the memory of third-party Starlark from stage 4 — section 2.3.

### 3.5. Version comparison

A new version of a module `module-kit` compares with each published version, withdrawn ones too, by the format's rules of version comparison: the principle of the parts, the table "change — version part", the rule of 0.y.z, the comparison of a check by meaning, the instances of a template by the values of the parameters and the eight rules `module-version.*` — [format text](../spec/format/README.md), section 27 (R89 spec; R101 spec). `module-kit` has no rules and no table of its own: R13 proposed them, and format 0.3 accepted them, with the corrections below, and the vectors `vectors/versions/` hold them as they hold the verdict (R17). The version of a module is semver `X.Y.Z` without pre-releases and build metadata (R46 spec); it is not the format version, MAJOR.MINOR, which `module_format_version` names (R44 spec). The code is written by the code epic.

- **Where format 0.3 differs from R13** (R101 spec; R17):
  - the IDs of the rules have the prefix `module-version.`, not names by parts: `module-version.above`, `module-version.step`, `module-version.retired-complete`, `module-version.retired-kept`, `module-version.retired-known`, `module-version.ids-kept` and `module-version.languages-kept`, and the eighth, `module-version.bands-kept`, holds the bands: the published bands stand first, in order and with the same IDs, and a new one only after the last;
  - the same version with another digest is a refusal of `module-version.above`, not of `module-index.one-package`; the index rule `module-index.version-above` holds the same at the build of the index ([format text](../spec/format/README.md), section 26);
  - a new entry of `retired_skills` is a major change, together with the retirement, and an entry is only expanded: a wrong one cannot be fixed in format 0.3;
  - a part also has "none": nothing has changed but the version, or the new version is the newest published one as it is;
  - a new version is compared with each published one, and CI of `modules` gives `diff` the package of each (architecture 3.7 spec): the 2026-11-02 amendment to R13, where `diff` took the other versions only if they were given, held until the answer to В15;
  - across a format transition the rules hold by the places of the package that the format keeps in all versions, and the part, while the format is v0, is major ([format text](../spec/format/README.md), section 2). Skills and IDs across a transition `diff` checks the same way as within one format version.
- **What is compared** are packages, not the author's YAML: the canonical view and the listing of the device part (section 3.2). The new version is the module's folder, which `diff` checks and builds in memory, or a package already built by `build`. The published versions are packages as files, each checked by the chain of digests from the index. A package of a previous format version is only `inventory.json` and `server.json`, which `diff` reads by the places that the format keeps in all versions. What does not go into the package — comments, the order of keys, `eval/`, files whose names begin with `.` — does not change the version: the package is the same.
- **The command `diff`:**

  ```
  module-kit diff [--json] (--index <module-index.json> | --first) [--published <package folder>]... <module>
  ```

  - `<module>` — a module's folder or a package's folder; they are told apart by `manifest.yaml` or `inventory.json` at the root. A module's folder `diff` checks and builds, as `check` and `build` do, and writes nowhere; a package built by `build` spares CI a second check with solvers;
  - `--index` — `module-index.json`, which CI has already checked by the recipe `release-verify`: the CLI checks no signatures (R77 spec). It reads the index by the places that the format keeps in all versions ([format text](../spec/format/README.md), section 26), — `moduleindex.Read` (R35), — and takes from it all the versions of the module and their format versions. `--first` says explicitly that there are no published versions, like the build of an index without a previous one (the 2026-11-02 amendment to R63 spec): a missing file will not pass silently;
  - `--published` — the folders of packages as files ([format text](../spec/format/README.md), section 25), without `device/`. `diff` recognizes a package by the digest of the bytes of `inventory.json` — this is the package digest —, and then checks `server.json` and, in the current format version, `device.json` against the inventory. Extra folders it skips, and the package of each version that the index names is needed: without it no comparison is possible;
  - code 0 — the version is accepted, the module has not changed, or this is the first version: `--first` or an index that does not name the module (R40); 1 — a refusal: a line for each breached rule, `refused: <ID>: <words>` (R37), or the report of the module check, as from `check`, if the check rejected the module; 2 — no comparison is possible: the call, input or output, a broken chain of digests, no package of a version that the index names;
  - the report: the module, the new version, with which versions it was compared, the part found, the allowed next versions and the raised part. Then the changes, a line each: the version part, the path — a JSON Pointer in the canonical view or in the listing of the device part —, and what changed; for instances — the values of the parameters. With `--json` — the same report as data;
  - the CLI does not go to the network: the index and the packages are put by CI of `modules` (architecture 3.7 spec).
- **The library** is one function over checked packages — the new one and the published ones — and the index; the CLI wraps it, and from stage 4 `module-registry` calls it (R17 spec). The same "same major" is read by `api` when it moves a learner to a new version (architecture 3.5 spec).
- **The code** (R36) — the package `moduleversion`:
  - `Compare(next, published)`: `next` — the `*modulepackage.Package` of the new version, `published` — `[]Published{Digest, Files}`, packages as files without `device/`. Each is read by `modulepackage.ReadParts` by the chain of digests — the inventory, `server.json` and `device.json`, without the files of the device part. The newest — by semver, withdrawn ones too; the same version with the same digest is `Unchanged`, and nothing is compared; without published ones — the first version. An error is a package that `ReadParts` did not accept, a package of format 0.2 — `ErrFormatVersion`, until T36 reads it, — a package of another module and two packages of one version;
  - `Changes(before, after)` — the part and the changes of two packages of one module and one format version. Each row of the table of the [format text](../spec/format/README.md), section 27, is at its own place, as in `versions.mjs` of `spec`, and everything else, except `manifest.version`, is a patch at each place where the JSON values of `server.json` and `device.json` diverged: by members and elements, and the `instances` of a template as a whole. A difference at the place of a table row or under it is not written, and under `skill_tiers` and `instances/<ID>` — when the skill graph or the task itself diverged. A check is compared by meaning through `normal.Compared` and `normal.Units` — `verdict` calls them too; answer slots — by their place in the item, `answer_slots/<j>` on a sheet and `line/<k>` in a workbook; the instances of a template — by the numbers of the parameters, through `template.Instance` of each version;
  - `Steps`, `StepPart` and `SameMajor` — the rule of 0.y.z: the next versions after a version and the part of each step, the part of the step to a version — `None` if it is not a next one, — and whether two versions have the same major, as `diff` and `api` read it. The numbers are raised by `semver.Version.Raise`, as text and without a bound;
  - the report — `Comparison{Module, Version, Published, Newest, Unchanged, Part, Next, Raised, Changes}`: `Next` — the next versions whose step raises a part no lower than the one found, `Raised` — the part of the step to the new version. `String()` writes the line of the module and the versions, the part found, the next versions and the raised part, and then a change per line — like a breach of the module check: `server.json #/tasks/apples: minor: the task apples is added`, for an instance — `on the instance a = 2, b = 3:` before the words. The changes go by part from major, then by place: `server.json` before `device.json`, and within a file — `schema.ComparePointers`. With `--json` — the same `Comparison` through `encoding/json`: `module`, `version`, `published`, `newest`, `unchanged`, `version_part`, `next_versions`, `raised` and `changes`, for a change — `part`, `file`, `pointer`, `parameters` and `what`, and a part — by its word;
  - the rules (R37) — `Comparison.Breaches`, a `Breach{Rule, Message}` per breach, and `Refused()`; `Rules` — the eight IDs in the order of the [format text](../spec/format/README.md), section 27. `module-version.above` — for each published version, withdrawn ones too; `module-version.step` — for the newest, only if `above` let it pass, by `Raised` and `Part`; the other six read only the places that the format keeps in all versions — the languages, the IDs of the bands in order, the keys of skills, tasks, lessons, traps and techniques, `retired_skills` with `replaced_by`, — so they hold across a format transition too. The report writes each breach as a line `refused: <ID>: <words>` before the changes, and `--json` as `breaches`. The words are as in `versions.mjs` of `spec`;
  - a format transition (R37): a published package whose inventory names an earlier format version is read by the chain — `inventory.json` by its digest, `server.json` by the digest and size from the inventory — and only by places: `Changes` does not compare it, and the part is major, while the format is v0, by one change of `inventory.json #/module_format_version`. A package of a newer format version is `ErrFormatVersion`: the format has not yet promised its places to a reader of this version. A package without a place that the format keeps is `ErrNotCanonical`;
  - the report is printed by the command `diff` (T38; R40) — `cmd/module-kit/diff.go` and `published.go`: the versions of the module — from `moduleindex.Read`, the package of each — among `--published` by the `package_digest` of the entry, `moduleversion.Published{Digest, Files}` from the folder; with `--json`, for a module that the check rejected — `{"check": [...]}` with the paths from the folder of the command line.
- **Tests:**
  - all the vectors of `format/vectors/versions/` from `spec.Format` — 152 cases at v0.9.2, the part found or a refusal with the rule's ID (R64 spec);
  - in the code (R36): since T35 — 119 cases with a part within one format version, the runner `versions` of the vector test, and since T36 also 30 refusals, each by its own rule and only by it, and three format transitions (R37); `TestPartsAreTheFormats`, `TestSteps`, `TestStepPart`, `TestSameMajor`, `TestChanges` — the places and the words on eight vectors, — `TestCompare`, `TestComparisonString` and `FuzzDiff` in `moduleversion`, `TestRaise` in `internal/semver`, `TestCompared` in `internal/normal`, `TestOrderOfPointers` — since T35 in `internal/schema` — and `TestReadParts` in `modulepackage`; since T36 — `TestRulesAreTheFormats`, `TestBreaches` — the words of each rule, the format transition, `earlier-format-older-version` and `newest-unchanged`, — `TestReadPublished` and `TestPlacesOf`;

  - **the tests** — `TestRulesAreTheFormats`, `TestBuildFirst`, `TestBuildNext`, `TestBuildRefuses`, `TestBuildErrors`, `TestTeachesOf`, `TestReadExamples`, `TestReadLaterVersion`, `TestReadRefuses`, `TestNewest`, `FuzzRead` and `FuzzBuildPrevious`, with an input that it found in `testdata/fuzz/`; in `module`, `TestNewerFormat`; in `internal/semver`, `TestParse`, `TestParseIsTheSchemas`, `TestCompare` and `FuzzCompare`. The valid examples of an index the runner `examples/valid` also holds to what the schema cannot say, as `indexFormProblems` of `spec` does: the root names the version of `format/VERSION`, and `teaches` is in order (`TestIndexForm`). The vector test passes the vectors of `indexes/` with the runner `indexes`: the package of each module of `modules/` by `modulepackage.Build`, the previous index by its canonical text, the index built byte for byte equal to the canonical text of the vector's `index`, a refusal only by the rule `refusal`, and `Read` reads both indexes back into the values of the vector.
