## 1. Назначение и границы

**Делает** — по карточке, architecture 3.7 spec:
- держит семантику формата модуля — одна библиотека на всех потребителей. Вердикт и проверка ключей при публикации зависят от одного кода видов проверки (R17 spec). При обновлениях R03 spec держат тест-векторы формата — `format/vectors/` `spec`: CI `spec` проходит их своей второй реализацией, а CI `module-kit` — все (R42 spec; repositories 3 spec);
- читает модуль автора — YAML 1.2.2 с ограничениями формата — и проверяет его по JSON Schema 2020-12 и правилам формата. Отказ называет ID правила (R45 spec). Что проверяется, перечисляет карточка:
  - схема, граф навыков без циклов, ссылки, навыки-опоры общей таксономии и зависимости паспорта (R49 spec, R50 spec);
  - задачи, проверки ячеек, каталоги ловушек и приёмов, уроки (R51 spec, R56 spec, R57 spec, R58 spec);
  - шаблоны со всеми экземплярами и их решателями (R60 spec, R61 spec);
  - тексты автора, которые ученик видит до решения, — проверкой утечки (concepts 10 spec; R57 spec).

  О картинке с прозрачными пикселями CLI предупреждает, но не отказывает (вторая поправка 2026-11-01 к R51 spec). О числе в тексте всего модуля — шаблоне ступени, совете ловушки, приёме, шаге решения — тоже предупреждает, но не отказывает ([текст формата](../spec/format/README.md), раздел 20; поправка 2026-11-08 к R57 spec) (R50, R52). С форматом 0.4 проверка держит и страницу рабочей тетради — раскладку по `page.yaml` и правила `task.workbook-page` и `lesson.workbook-page`, — разобранный пример на тетради с `lesson.example-fills`, вид `time`, признак `notation: word` у выбора от руки, пути картинок шаблона с подстановками, наводящий вопрос и описание шага в проверке утечки, нумерованный список урока и правило `yaml.printable` ([текст формата](../spec/format/README.md), разделы 2, 4, 14, 15, 18, 20, 21 и 23; R52);
- читает версии формата модуля в окне. Пока формат v0, в окне только текущая версия, 0.4, а модуль 0.3 и старше отклоняется (R17; R52). Модуль проверяется, собирается и исполняется по версии, которую называет его паспорт, а модуль вне окна отклоняется с причиной (R44 spec);
- собирает пакет модуля и индекс модулей (R17 spec):
  - пакет — канонический вид с ярусом каждого навыка и числами каждого экземпляра шаблона, часть для устройства и опись (R62 spec);
  - индекс — из индекса прошлого релиза, с записью каждой опубликованной версии по дайджесту пакета и с отметками о снятии (R63 spec).

  Пакет — подписанная версия модуля, адресуемая по содержимому, индекс — подписанный накопительный список опубликованных версий (concepts 15 spec). На релизе `modules` их собирает CLI `module-kit` (repositories 4 spec);
- сравнивает новую версию модуля с каждой опубликованной, снятые тоже, по правилам сравнения версий формата и сверяет упразднённые навыки: снятие ID навыков не освобождает ([текст формата](../spec/format/README.md), раздел 27; concepts 3 spec; R89 spec). Пакет прошлой версии формата он читает по местам, которые формат держит во всех версиях, и через переход формата сверяет навыки и ID так же ([текст формата](../spec/format/README.md), раздел 2). Часть версии сравнение находит само, а у CLI для него своя команда `diff` (R13; раздел 3.5);
- заполняет шаблоны задач (concepts 9.3 spec; R60 spec):
  - перебирает сочетания параметров — не больше 10 000 на шаблон — и строит экземпляры;
  - ключ каждого экземпляра считает решатель ещё при проверке модуля (R61 spec);
  - экземпляр попытки выбирает генератор от её зерна (R59 spec; раздел 3.3);
- строит открытый вид задачи — без ключа, решения и ловушек — по пометкам `x-open` в схемах формата: поле без пометки закрыто (architecture 1 spec; R05 spec; R45 spec). Открытые виды он строит на сервере из части пакета для сервера, и в пакет они не входят (R62 spec);
- держит виды проверки и нормализацию: в формате v0 это `number`, `fraction`, `choice`, `predicate` и `rubric` (concepts 9.2 spec; R56 spec). Это код платформы, общий для всех модулей: модуль только выбирает вид и задаёт параметры (R02 spec);
- выносит вердикт: сравнивает наблюдение с ключом или условием (architecture 1 spec; concepts 9.1 spec; R03 spec). Вердикт допускается, только если ключ или условие дал автор, решатель или взрослый, а при ключе, выведенном ИИ, вердикта нет (concepts 9.4 spec; R04 spec);
- сводит наблюдения двух читателей в одно, по проверке ячейки, и выносит вердикт по сведённому наблюдению целиком, с причинами «не прочитать» из наблюдения (R86 spec; [текст контрактов](../spec/contracts/README.md), раздел 10). Тем же кодом он выносит eval-раннеру `tutor` вердикт по истине разметки образца (R95 spec);
- держит проверку утечки — поиск ключа и фраз-утечек, которые указал автор (concepts 10 spec; R57 spec). `api` проверяет ею текст наставника до того, как он уйдёт на устройство (architecture 3.5 spec), а проверка модуля — тексты автора (concepts 10 spec);
- исполняет Starlark в песочнице, как в standalone (repositories 7 spec), — в go.starlark.net той версии, которую называет формат, и в одном диалекте на весь Starlark формата (R88 spec):
  - условия проверки — счёт шагов, дошедший до 1 000 000, или ошибка дают «без проверки» (R56 spec; R88 spec);
  - решатели шаблонов — не больше 100 000 000 шагов на все экземпляры шаблона (R61 spec).

  Часы, одновременные запуски и версия интерпретатора — раздел 3.4;
- сверяет пакет по цепочке дайджестов от индекса, который закрепил pull request `api`: индекс → опись → части → файлы (R62 spec, R63 spec). Подписей библиотека не проверяет: подпись файла релиза проверяет рецепт `spec` `release-verify` там, где файл входит в NovaTrail (R77 spec; поправка 2026-11-01 к R17 spec);
- даёт автору CLI: проверить модуль, собрать пакет, построить индекс и сравнить версии — `diff` (R13; раздел 3.5), — а сборке страницы образцов `canvas` отдаёт открытые виды и медиафайлы командой `open`: у шаблона — экземпляр по зерну, и у каждой задачи — дайджест её открытого вида (R15; R93 spec). Команды — раздел 3.6. Индекс CLI строит внутри общего релиза `modules`, после номера и до публикации (architecture 3.7 spec; R63 spec). «Собрать» пишет пакет файлами, а архив пакета для релиза кладёт рецепт `modules` (R03 modules). Снятия «построить индекс» читает файлом `withdrawals.yaml` `modules` — по `$defs/withdrawals` схемы индекса ([текст формата](../spec/format/README.md), раздел 26).

**Не делает:**
- не обращается к ИИ (architecture 3.7 spec). Работу читает `tutor`, а `module-kit` получает от `api` уже наблюдение (architecture 1 spec; architecture 3.5 spec);
- не ходит в сеть: библиотека — вычисления без ввода-вывода, а CLI только читает и пишет файлы модуля (architecture 3.7 spec; repositories 1 spec). Прошлый индекс сборка получает файлом: его скачивает и проверяет общий релиз `.github` (поправка 2026-11-02 к R63 spec);
- не хранит данных учеников (architecture 3.7 spec): из частей платформы их на сервере хранит только `api` (architecture 1 spec; R15 spec);
- не владеет форматом. Схемы, текст формата, примеры и тест-векторы лежат в `format/` `spec` (R42 spec; R45 spec; repositories 5 spec), а `module-kit` держит семантику формата в коде (R17 spec). CI `spec` проверяет примеры валидатором JSON Schema, а векторы — своей второй реализацией, без `module-kit`: иначе `spec` зависел бы от того, кто зависит от него (repositories 3 spec);
- не задаёт генератор случайности и вывод зёрен. Их задаёт `spec`, с тест-векторами, а `module-kit` их проходит (architecture 1 spec). Генератор — PCG из `math/rand/v2` Go, а места случайности выводятся, как у стенда standalone (R59 spec). Они одни на всю платформу — на `module-kit`, виджеты, `engine` и `sim` (R27 spec);
- не подписывает пакеты и индекс и не проверяет подписей: подпись ставит общий workflow релиза из `.github`, а проверяет рецепт `spec` `release-verify` (R17 spec; R77 spec; repositories 4 spec);
- не выбирает урок или задачу и не считает модель ученика: это `engine` и `learner-model` (architecture 1 spec). Типы графа у них простые и не из `module-kit`: задаёт их `learner-model`, а `engine` берёт у него (architecture 3.8 spec; R28 spec);
- не публикует модули: реестр v0 — подписанный индекс, который собирает CI `modules`. Сервис реестра появится на этапе 4 и тоже будет построен на `module-kit` (R17 spec).

**Данные и связи:**
- своих данных нет: он работает с модулем, пакетом и индексом, которые ему дают. Данных учеников и секретов нет, как ни в одном репозитории (architecture 3.7 spec; RULES.md, Hard rules). В процессе `api` он получает наблюдение и ключ или условие задачи и возвращает вердикт (architecture 3.5 spec);
- при сборке ни от чего не зависит, кроме `spec` (repositories 2.1 spec; repositories 3 spec):
  - схемы, примеры и векторы формата он берёт модулем Go `github.com/altnovatrail/spec` — `spec.Format` по тегу релиза, тому же, что у подмодуля `spec/`, — а не из подмодуля;
  - типы частей, их открытых видов, канонического вида, описи и индекса — из пакетов `types/formatv0` и `types/formatv0/open` того же модуля (R64 spec, R72 spec);
  - наблюдение — пакет контракта `novatrail.observation.v1` вложенного модуля Go `github.com/altnovatrail/spec/contracts`, который `spec` генерирует по контрактам API, а векторы сведения и вердикта по наблюдению — `contracts.Vectors` того же модуля (R86 spec; поправка 2026-11-03 к R64 spec). Наблюдением `tutor`, `module-kit` и `api` обмениваются в одном процессе, и тип у него один (R83 spec). Модуль `contracts` требует рантайм protobuf и connect-go: это сторонние модули Go, а не репозитории. С T28 пакет `observation` берёт рантайм protobuf, BSD-3-Clause, и `ci-licenses` его видит, а connect-go в сборку не входит (R29; раздел 3.1).

  Версию модуля `spec` в `go.mod` и подмодуль двигают вместе, переходом на тег, а из Dependabot `gomod` модуль `spec` исключают (R64 spec). Так же — вложенный модуль `spec/contracts`: его тег `contracts/vX.Y.Z` несёт номер тега `spec`, и модуль, подмодуль и пакет двигают одним переходом (R64 spec; R83 spec). Оба модуля в `go.mod` с T19, на v0.9.2, Dependabot их не поднимает, а `ci-lint` сверяет их версии с подмодулем (R20; раздел 3.1);
- его импортируют `api` и eval-раннер `tutor`, а CLI по точному тегу берут CI `modules` и CI `canvas` — бинарником релиза, который сверяет `release-verify` до первого запуска (repositories 1 spec; repositories 3 spec; R77 spec). CI `canvas` берёт CLI, чтобы собрать страницу образцов: открытые виды и медиафайлы она получает при сборке, из пакетов релиза `modules` (R25 spec; architecture 3.2 spec). Для этого у CLI своя команда, `open` (R15; раздел 3.6). Позже, на этапе 4, на нём строятся `module-registry` и `module-pipeline` (architecture 3.7 spec; repositories 2.1 spec);
- `sim` его не берёт: часть пакета для сервера он читает по типам канонического вида из `spec` (architecture 3.9 spec; R62 spec). `learner-model` и `engine` пакетов не читают: граф им передаёт `api` (architecture 3.8 spec);
- вердикт воспроизводим. Попытка хранит дайджест своего пакета — дайджест описи, — версию формата модуля, версию `module-kit` и зерно. Вердикт повторяется по сохранённому наблюдению, без ИИ, тем релизом `module-kit`, который его вынес (architecture 1 spec; R03 spec; R44 spec). Изменение поведения вида проверки — новая версия формата (R44 spec);
- новую модель ИИ допускают по eval, и ложные тревоги там считаются по вердикту, через `module-kit` (architecture 4.6 spec; repositories 4 spec);
- проверки CI пришли ещё до кода: общие проверки из `.github`, среди них `docs-check-repo`. Какие они и что держит мерж — R30 spec и architecture 3.11 spec. Подключила их T17 `spec`, и файлы CI сюда писала её сессия; файлы CI под свой код пишет сессия этого репозитория (поправка 2026-10-21 к R30 spec).
  - Находки CodeQL, Scorecard и SonarCloud закрываются перед новой задачей (правило 12 [RUN.md](../RUN.md)), а общие для всех репозиториев причины тех, что остаются открытыми, записаны в R33 spec.
  - Проверки Go пришли с заготовкой CLI (R04): рецепты у них свои, а запускает их обёртка Go — общий `go.yml` `.github`, который на ней и проверен (R16 .github). Go CodeQL читает с T12: общий `codeql.yml` `.github` v0.1.3 собирает его с Go из стадии `toolchain` (R06). Обёртка TypeScript проверяется на первом коде на TypeScript, у `canvas` (repositories 6 spec; architecture 3.11 spec).
  - Релиз выпускает общий `release.yml` `.github`, а файлы для него собирает свой рецепт `release-files` (R07; раздел 3.1).
  - Код приходит со своими тестами. С T18 покрытие тестов уходит в Codecov, а мерж ждёт `codecov/patch` — не меньше 90 % изменённых строк, — как только автор поставит её в ruleset `main` (RULES.md, How we work; R48 spec; R18; раздел 3.1);
- этап 1, вместе с `modules`: формат модуля сразу проверяется на трёх модулях двух предметов (repositories 6 spec; R08 spec; R41 spec; product 11 spec). Работу по порядку repositories 6 spec ведёт сквозной план — COORDINATION.md `spec`. У `module-kit` там закрыты строки 3.1 и 3.2 — переход на линию 0.6 и детализация, — а открыта 3.3, эпик кода, E2 (R76 spec).

## 2. Решить при детализации

Пункты «Решить при детализации» из карточки — по подразделу на пункт. Каждый, кроме 2.6, решила своя задача эпика E1 — он сделан и лежит в архиве, [plan/E1.md](plan/E1.md). Решённый пункт называет запись журнала, а само решение переезжает в раздел 3. Вопрос, который выходит за этот репозиторий, уходит «в реестр spec» (RULES.md, Across repositories).

У карточки четыре пункта — подразделы 2.1–2.4. ### 2.1. Пакет модуля и канонический текст

- **Суть:** как `module-kit` собирает пакет модуля по R62 spec и чем пишет его канонический текст. Состав пакета решил формат, а здесь решалось, как его исполнить.
- **Решено** (R09): канонический текст пишет своя функция, которая останавливается на значении вне формата, а канонический вид собирается из JSON-значения каждого файла как есть. Устройство пакета — раздел 3.2.
- **Задача:** T01.

### 2.2. Генератор в CI

- **Суть:** чем `module-kit` исполняет генератор и места случайности по R59 spec — стандартной библиотекой Go или своим кодом — и как его CI проходит векторы `format/vectors/random/` `spec`.
- **Решено** (R10): генератор — свой код по константам [текста формата](../spec/format/README.md), раздел 22, с ошибкой на аргументе вне области, а `math/rand/v2` и `hash/fnv` — только эталон в тестах. Генератор лежит в `internal/`, а наружу идёт выбор экземпляра попытки. Устройство — раздел 3.3.
- **Задача:** T02.

### 2.3. Часы, одновременные запуски и память Starlark

- **Суть:** сколько времени у вычисления условия проверки и у решателя шаблона, сколько их идёт сразу, кто держит часы и места, что значат сработавшие часы, сколько памяти у песочницы и нужен ли отдельный процесс. Шаги, диалект и место решателя решил формат, а часы и одновременные запуски он оставил `module-kit` (architecture 3.7 spec).
- **Решено** (R11): go.starlark.net — той версии, которую называет формат: с 0.3 это 4f4267fb140d, и диалект, один на весь Starlark формата, условие тоже, формат называет сам (R88 spec; R17). Часы — страховка `module-kit`: 1 с на условие и 60 с на решатель шаблона. Мест библиотека не держит: одновременность — у вызывающего, у `api` — не больше `GOMAXPROCS` сразу (architecture 3.7 spec). Устройство — раздел 3.4.
- **Отложено:** память стороннего Starlark. С этапа 4 условия в `api` и решатели в `module-registry` пишут и сторонние авторы, а go.starlark.net памяти не считает. `spec` ответил на В12 дополнением к О-9: с этапа 4 Starlark стороннего модуля исполняется в отдельном процессе с пределом памяти, а как — решают задачи `api` и `module-registry` (architecture 3.5 и 3.13 spec). До тех пор — Д10 в таблице 4 [RUN.md](../RUN.md).
- **Задача:** T03.

### 2.4. Правила semver для `diff`

- **Суть:** по каким правилам `module-kit` сравнивает новую версию модуля с прошлой: что поднимает мажорную, минорную и патч-версию, что сравнение находит само, а что объявляет автор. С v0.6.4 карточка называет сравнение среди пунктов «Решить при детализации»: новая версия сравнивается с каждой опубликованной ниже неё по semver, снятые тоже (architecture 3.7 spec; R12). Раньше его называла только задача, которая завела этот репозиторий (T05 `spec`). Команды `diff` в карточке нет: CLI там — «проверить, собрать, построить индекс». Отдельная это команда или часть проверки, решает задача.
- **Решено** (R13): сравнение само находит наименьшую часть версии, а автор может поднять выше, но не ниже. Мажорная — когда что-то из того, что было у ученика прошлой версии, ушло или значит другое. Сравниваются пакеты, а у CLI для сравнения своя команда, `diff` — раздел 3.5. Таблицу «изменение — часть версии», правила сравнения и то, с какими версиями сравнивать, формат 0.3 взял себе — ниже.
- **Ответ spec:** на В14 и В15 — формат 0.3 (R89 spec; R101 spec; R17). Принцип частей, таблица «изменение — часть версии», правило 0.y.z и правила сравнения теперь в [тексте формата](../spec/format/README.md), раздел 27, с векторами `vectors/versions/`, а ID правил — `module-version.*`. Новая версия сравнивается с каждой опубликованной, а пакет прошлой версии формата читается по местам, которые формат держит во всех версиях ([текст формата](../spec/format/README.md), раздел 2). Чем ответ расходится с R13, — раздел 3.5.
- **Задача:** T04.

### 2.5. Команда CLI для открытых видов

- **Суть:** нужна ли CLI `module-kit` своя команда, которая отдаёт открытые виды задач сборке страницы образцов `canvas`, или этой сборке хватает команд карточки — проверить, собрать, построить индекс (architecture 3.7 spec). Вопрос R25 spec оставил детализации `module-kit`, и поправка 2026-10-28 к R25 spec оставила его там же. Решается здесь: CLI — часть `module-kit` (R17 spec). Новая команда меняет карточку, и её правку итог детализации отправляет строкой таблицы 3 «в реестр spec» (раздел 2).
- **Решено** (R15): своя команда `open` на релиз `modules`. Она пишет файл открытых видов — у каждого модуля по его новейшей неснятой версии ID, версию, дайджест пакета, открытые виды паспорта и задач, как в `tutor-open-tasks`, — и медиафайлы задач, `LICENSE` и `NOTICE`, сверенные по описи. Снятые версии она пропускает. Строится последней задачей эпика кода, после первого релиза (поправка 2026-11-04 к R16). Устройство — раздел 3.6.
- **Ответ spec:** что `open` отдаёт у шаблона и как считается дайджест открытого вида, решил протокол eval — ответ на В17 (R93 spec; R17). У шаблона — экземпляр по зерну, а дайджест открытого вида — `sha256:` и SHA-256 его канонического текста, у экземпляра — с подставленными числами.
- **Задача:** T05; команду построила T40 (R43).

### 2.6. Тип наблюдения

- **Суть:** вердикт `module-kit` выносит по наблюдению — тому, что `tutor` прочитал в работе (architecture 3.5 spec). Наблюдением `tutor`, `module-kit` и `api` обмениваются в одном процессе, и тип у него один — код, который `spec` генерирует по контрактам во вложенный модуль Go `spec/contracts` (R83 spec).
- **Ответ spec:** контракт наблюдения пришёл с эпиком E3 `spec` — пакет `novatrail.observation.v1` модуля `spec/contracts` (R86 spec; R17). Два чтения сводит в одно `module-kit`, по проверке ячейки, и по сведённому наблюдению выносит вердикт; как, говорит [текст контрактов](../spec/contracts/README.md), раздел 10, а векторы — `contracts.Vectors`. Формат модуля от этого не меняется: вердикт по прочитанному значению остаётся по [тексту формата](../spec/format/README.md), раздел 15.
- **Решено** (R29): пакет `observation` поверх `verdict` — `Validate`, `Join`, `Verdicts` и `Essay`. Негодное наблюдение — ошибка `ErrNotValid`, так что `unchecked` в вердикте по годному наблюдению — `unchecked` условия. `verdict` остаётся без protobuf. Устройство — раздел 3.6.
- **Задача:** T28 эпика кода, E2.

### 3.2. Пакет модуля

Пакет собирает CLI на релизе `modules`, из папки модуля, по версии формата, которую называет его паспорт ([текст формата](../spec/format/README.md), раздел 25; R62 spec). Пакет собирается только из модуля, который прошёл проверку: схему и все правила формата (R45 spec). Код принесла T33 (R34): `modulepackage.Build(ctx, fsys)` сначала проверяет модуль `module.Check` и модуль с нарушениями отвергает `*Refusal` с отчётом, а пакет отдаёт байтами его файлов, `Package.Files`, — на диск их пишет CLI, T37; `modulepackage.Read(fsys, digest)` читает пакет файлами по цепочке дайджестов; канонический текст — `internal/canonical.Text`.

- **Части пакета** (concepts 15 spec):
  - часть для сервера — канонический вид, `server.json`: модуль одним JSON-объектом, со всем содержанием, и ключами, решениями и ловушками тоже;
  - часть для устройства — `LICENSE`, `NOTICE` и медиафайлы, а когда в формате будут виджеты, — их бандлы. Её называет список, `device.json`;
  - опись — `inventory.json`: версия формата, ID и версия модуля и обе части по дайджестам и размерам. Это не паспорт модуля, хотя паспорт в коде и схемах называется `manifest`.
- **Как он собирается:**
  1. Читатель YAML даёт JSON-значение каждого файла части (R45 spec). Файлы и папки на `.`, комментарии и `eval/` в пакет не идут.
  2. Канонический вид: части модуля — под своими членами, `manifest`, `skill_graph`, `traps`, `techniques` и `solving_steps`, а `tasks` и `lessons` — объектами по локальному ID. Значение части — JSON-значение её файла как есть: шаблон — как написан, и значений по умолчанию нет (R09). Сверх частей — `skill_tiers`, ярус каждого навыка, по [тексту формата](../spec/format/README.md), раздел 12, если у модуля есть граф навыков, и `instances`, числа и результаты решателя каждого экземпляра шаблона, по [тексту формата](../spec/format/README.md), разделы 23 и 24, если среди задач есть шаблоны. Члена без своей части — и `skill_tiers` без графа навыков, и `instances` без шаблонов — в виде нет. Целое, которое читатель YAML дал как double, — `50.0` или `5e1`, — идёт в вид целым `50` ([текст формата](../spec/format/README.md), раздел 25).
  3. Список части для устройства — объект: `license` — дайджест и размер `LICENSE`; `notice` — `NOTICE`, только если он есть; `media` — каждый файл `media/` по пути от `media/`, только если такие файлы есть (`inventory.schema.json`, `$defs/device_listing`).
  4. Опись: `module_format_version`, `id` и `version` — как в паспорте, а `server_part` и `device_part` — дайджест и размер канонического текста канонического вида и списка.
  5. Дайджест пакета — дайджест канонического текста описи. Пакет файлами — папка: `inventory.json`, `server.json` и `device.json` — канонические тексты описи, канонического вида и списка, — и `device/` с `LICENSE`, `NOTICE` и `media/<путь>` побайтно. Так их пишет «собрать», а архив пакета для релиза кладёт рецепт `modules` (R03 modules; architecture 3.7 spec).

  Пакет зависит только от файлов модуля и версии формата его паспорта: версии `module-kit`, времени и путей в нём нет (R62 spec).
- **Канонический текст** пишет своя функция над деревом JSON-значений — объект, массив, строка, целое, `true`, `false`, `null` (R09):
  - члены объекта идут по порядку кодовых единиц UTF-16 их имён, а между лексемами пробелов нет;
  - целое пишется десятичными цифрами, отрицательное — со знаком `-`;
  - в строке экранируются только `"` и `\`, `\b`, `\t`, `\n`, `\f` и `\r`, а прочие знаки до U+001F пишутся как `\u00` и две строчные шестнадцатеричные цифры. `<`, `>`, `&`, U+2028 и U+2029 пишутся как есть, и знаки не нормализуются;
  - текст — UTF-8, без BOM и без перевода строки в конце;
  - на числе с дробной частью, целом вне ±(2^53−1), строке не из корректного UTF-8 и значении не из JSON функция останавливается с ошибкой. На проверенном модуле такой отказ значит дефект в коде `module-kit` (R09). Тексты пакета и индекса модулей пишет только она: не `encoding/json`, не `jsontext` и не проход по типам `formatv0`.
- **Дайджест** — `sha256:` и 64 строчные шестнадцатеричные цифры от байтов, а размер — их число (concepts 15 spec). Дайджест пакета хранит попытка (architecture 1 spec).
- **Чтение пакета** идёт по цепочке дайджестов от дайджеста пакета, который закрепил индекс: опись → части → файлы. Подписей библиотека не проверяет (R62 spec, R63 spec, R77 spec). Сверх дайджестов `Read` держит версию формата описи, схему и канонический текст каждого из трёх текстов и то, что паспорт вида называет модуль описи; отказ — `ErrChain`, `ErrFormatVersion` или `ErrNotCanonical`, с путём файла (R34). JSON читает `canonical.Parse`, общий с индексом: текст не в UTF-8 и число вне double — не JSON, `ErrNotCanonical`. До T34 число вроде `1e700` в описи роняло `Read` паникой валидатора схем (R35). `ReadParts` — то же чтение без файлов `device/`: так сравнение версий читает опубликованный пакет, который CI `modules` даёт без части для устройства, а её сравнивает по списку (R36).
- **Кто читает пакет:**
  - через `module-kit` — `api`, по дайджесту, и eval-раннер `tutor`, а с этапа 4 — `module-registry` (architecture 3.10 spec; R17 spec);
  - через CLI `module-kit` — CI `canvas`, для страницы образцов (R25 spec);
  - без `module-kit` — `sim`, по типам канонического вида из `spec` (architecture 3.9 spec);
  - часть для устройства раздаёт `api` (architecture 3.10 spec).
- **Где лежит:** на этапе 1 пакеты и индекс лежат в релизах `modules`, на этапе 2 пакеты лежат и в образе `api`. Для повтора вердикта старые версии пакетов берутся из релизов `modules` (architecture 3.10 spec; Т-17).
- **Тесты:**
  - все векторы `format/vectors/packages/` и `format/vectors/tiers/` из `spec.Format` (R64 spec). Результаты решателя вектора `with-solver` CI считает своим запуском (Д44 в таблице 4 RUN.md `spec`);
  - модульные тесты таблицы экранирования и каждого отказа;
  - fuzz-тест, который сверяет функцию с `jsontext.Value.Canonicalize` на значениях, допустимых в формате. Он лежит в файле с `//go:build goexperiment.jsonv2`, и при `GOEXPERIMENT=nojsonv2` остальные тесты идут без него (R09);
  - в коде (R34): векторы `packages/` — исполнитель `packages` теста векторов, `tiers/` — с T24; `TestEscapes`, `TestEveryControlCharacter`, `TestText`, `TestRefusals`, `TestDigest` и `FuzzText` в `internal/canonical`; `TestBuildFiles`, `TestBuildLeavesOut`, `TestBuildRefuses`, `TestBuildContext`, `TestIntegers`, `TestRead`, `TestReadRefuses` и `FuzzRead` в `modulepackage`, а разбор JSON, `canonical.Parse`, с T34 общий с индексом, — `TestParse` в `internal/canonical` (R35).

### 3.3. Генератор и места случайности

Генератор и места случайности `module-kit` исполняет по [тексту формата](../spec/format/README.md), раздел 22 (R59 spec), своим кодом (R10). Код принесла T30 (R31).

- **Пакет** — `internal/random`: в API библиотеки он не входит, и другие модули Go его не импортируют. Генератор один на платформу по алгоритму, а не по коду: `engine`, `sim` и виджеты исполняют его сами и проходят те же векторы (R27 spec; R59 spec).
- **API пакета** (R31) — `New(high, low)` — поток от двух слов; `Words(seed, names)` — слова места, а `Place(seed, names...)` — его поток; у `Stream` — `Integer`, `Below`, `Between`, `Fraction` и `Permutation`, по функции формата на метод, а `MaxPermutation` — 2^31 − 1. Отказ функции и места — `ErrDomain`, с сообщением, что не так.
- **Поток** — два слова состояния, старшее и младшее, взятые как есть. Шаг — `state · M + C mod 2^128` через `bits.Mul64` и `bits.Add64`, выход — DXSM, а константы — числами из текста формата. Общего состояния нет: поток живёт в одном вызове.
- **Место случайности** — зерно, целое без знака в 64 бита, и список имён. Его поток начинают два слова: FNV-1a 64 от UTF-8 текста «зерно десятичными цифрами, затем `|` и имя — для каждого имени» и само зерно. Имён хотя бы одно, а имя — непустая строка из корректного UTF-8 без `|`; иначе место не строится, а возвращается ошибка. Так же, на `math/rand/v2` и `hash/fnv`, выводит поток `seeded` стенда standalone — место главного зерна с именами «эксперимент, единица, назначение», — а в рабочем коде standalone генератора от зерна нет (R59 spec; раздел 4).
- **Функции** — пять, те, что проверяют векторы. Каждая берёт столько целых, сколько велит текст формата:

  | Функция | Область | Как считает |
  |---|---|---|
  | `integer` | — | следующее целое потока |
  | `below(b)` | b от 1 до 2^64 − 1 | степень двойки — маской; иначе метод Лемира: старшее слово произведения целого на b, с отбраковкой, пока младшее слово меньше (2^64 − b) mod b |
  | `between(a, c)` | a ≤ c и c − a + 1 ≤ 2^63 − 1. Сначала проверяется a ≤ c, а затем, без переполнения, что `uint64(c) − uint64(a)` не больше 2^63 − 2 | a + `below(c − a + 1)` |
  | `fraction` | — | младшие 53 бита следующего целого, делённые на 2^53 |
  | `permutation(n)` | n от 0 до 2^31 − 1 | от 0, 1, …, n − 1 по порядку, а для i от n − 1 до 1 — обмен мест i и `below(i + 1)` |

  На аргументе вне области функция возвращает ошибку и целых не берёт. Тасования списка нет: векторов у него нет, а `module-kit` ничего не тасует (R10).
- **Экземпляр попытки** — одна функция API шаблонов, `template.AttemptInstance(seed, task, count)` (R31): номер `below(count)` места зерна попытки с именами `template`, ID задачи и `instance`, при count от 1 до 10 000, `template.MaxInstances` (R60 spec; [текст формата](../spec/format/README.md), раздел 23). Номер — с 0, по порядку счётчика, а count — число экземпляров, чьи числа несёт пакет: функция шаблона не берёт и экземпляров не считает. Count вне области и ID, который не имя места, — `template.ErrDomain`. Других вызовов это место не делает, а других мест у модуля в формате v0 нет. ID задачи — строчные латинские буквы, цифры и `-` (`common.schema.json`), и имя места из него всегда допустимо. Зерно попытки берёт `api` из криптостойкого источника, а `module-kit` получает его числом. Ни зерно, ни слова места на устройство не уходят: по словам видно зерно ([текст формата](../spec/format/README.md), раздел 22).
- **Чего в коде нет:** случайности не от зерна — ни `math/rand`, ни функций верхнего уровня `math/rand/v2`, ни `crypto/rand`. `math/rand/v2` и `hash/fnv` есть только в тестах.
- **Тесты:**
  - все векторы `format/vectors/random/` из `spec.Format` (R64 spec). Вектор читают читатель YAML и валидатор схем проверки модуля — по `random-vector.schema.json` — и тип `formatv0.RandomVector` (R72 spec), а числа-строки разбирает `strconv`. Если даны зерно и имена, выведенные слова сравниваются с `state`. Затем вызовы идут по порядку, и каждое значение сравнивается, `fraction` — как double. Тест падает, если векторов нет и если у вызова нет известного поля;
  - место шаблона проверяют и векторы `format/vectors/templates/`: по каждому зерну они называют экземпляр. Номер экземпляра 16 зёрен пяти векторов без решателя держит `TestAttemptInstanceOfTheVectors` в `template`, вместе с тем, что `Instances` на этом номере даёт параметры попытки, а векторы целиком проходит тест векторов (R32);
  - модульные тесты — каждый отказ и число целых, которое берёт каждая функция: `below(1)` и `between(a, a)` берут одно, `permutation(0)` и `permutation(1)` — ни одного (`TestWords`, `TestDraws`, `TestRefusals`, `TestEdges`);
  - сверка со стандартной библиотекой: поток, функции и слова места сравниваются с `math/rand/v2` и `hash/fnv`, а состояние потока после каждой функции — с `PCG.MarshalBinary`. Обычный тест, `TestReference`, идёт на каждом `go test` — на словах всех векторов, на границах 1, степенях двойки, 2^63 − 1, 2^63 + 1 и 2^64 − 1 и на 5 000 входов от самого генератора с постоянным зерном. Fuzz-тест, `FuzzReference`, сверяет то же на любых входах, с перестановками до 1024 чисел, и те же входы, кроме входов от генератора, лежат в его корпусе. Эталон живёт только в тестах, и тега сборки им не нужно (R10).

### 3.4. Песочница Starlark

Starlark формата — условия проверки, выражения шаблонов и решатели — `module-kit` исполняет в go.starlark.net, в процессе вызывающего (R11). Код — пакет `internal/sandbox` (R28, R33).

- **Лимиты:**

  | Лимит | Что держит | Кто держит | Откуда число |
  |---|---|---|---|
  | условие — не длиннее 1000 знаков | размер выражения | проверка модуля, по схеме | формат (R56 spec) |
  | условие — счёт шагов не доходит до 1 000 000 | шаги одного вычисления в счёте закреплённой версии go.starlark.net | `Thread.SetMaxExecutionSteps`: счёт дошёл до предела — «без проверки» | формат (R56 spec; R88 spec) |
  | часы условия — 1 с | время вычисления, чьи шаги зовут тяжёлые встроенные функции | `module-kit`, константа релиза; сработали — «без проверки» | замер 2026-11-02: простое условие тратит на 1 000 000 шагов 6 мс (R11) |
  | выражение шаблона — не длиннее 1000 знаков, шагов не больше, чем лексем; сочетаний — не больше 10 000 на шаблон | цена перебора экземпляров | проверка модуля: длина — по схеме, сочетания — правилом `task.template-instances`; предела шагов и часов у выражения нет (R32) | формат (R60 spec) |
  | решатель — не длиннее 8192 знаков | размер программы | проверка модуля, по схеме | формат (R61 spec) |

  | часы решателя — 60 с на шаблон | время программы, чьи шаги зовут тяжёлые встроенные функции | `module-kit`, константа релиза; сработали — нарушение `task.template-solver` | замер 2026-11-02: простой цикл тратит на 100 000 000 шагов 0,45 с (R11) |
  | рекурсия выключена | стек Go от рекурсии функций Starlark: его переполнение роняет весь процесс | диалект, `Recursion: false`; go.starlark.net ловит и рекурсию через `lambda`. Встроенные функции на глубоко вложенных значениях она не держит — их держит, как и память, только отдельный процесс | формат: у решателя — R61 spec, у условия — R88 spec |
  | одновременные запуски | CPU процесса и стенное время часов | вызывающий: `api` — не больше `GOMAXPROCS` сразу, CLI — решатель на CPU | R11; у `api` — architecture 3.7 spec |
  | паника интерпретатора | процесс вызывающего | `module-kit`, `recover`: «без проверки» или нарушение `task.template-solver` | R11; #672 go.starlark.net |
  | память | процесс вызывающего | до этапа 4 — никто: go.starlark.net её не считает. С этапа 4 Starlark стороннего модуля — в отдельном процессе с пределом памяти у вызывающего | Д10; О-9 |
  | версия go.starlark.net | счёт шагов и поведение языка | формат называет её — 4f4267fb140d, — а `module-kit` закрепляет в `go.mod` и исключает из Dependabot `gomod` | формат (R88 spec); R11 |

  Шаги считает go.starlark.net той версии, которую закрепил `module-kit`: с 2026-10-05 счётчик растёт на 10 за обратный переход или вызов, а раньше рос на 1 за инструкцию (раздел 4). Тот же модуль на тех же значениях делает те же шаги на любой машине, но не в другой версии интерпретатора: поэтому версию называет формат, и её смена — мажорная версия формата. Предел срабатывает, когда счёт доходит до него, а формат 0.2 останавливал вычисление только за пределом (R88 spec; [текст формата](../spec/format/README.md), раздел 2).
- **Вызов.** Вычисление идёт синхронно, в потоке вызывающего, на своём `starlark.Thread` и с `context` вызывающего. Часы `module-kit` и отмена `context` зовут `Thread.Cancel` с разными причинами. Первые дают «без проверки» или нарушение правила, вторая — ошибку без вердикта. Отмену интерпретатор видит между инструкциями, а встроенную функцию не прерывает: `len(list(range(50000000)))` при часах 100 мс останавливается через 0,2 с после них, взяв 763 МиБ, а `str` списка глубиной 1 000 000 идёт больше 120 с на одном шаге (R11). Часы идут по стенному времени, поэтому вызывающий держит одновременных вычислений не больше `GOMAXPROCS` (architecture 3.7 spec). Мест и общего состояния у песочницы нет.
- **Диалект** — один на весь Starlark формата, как в [тексте формата](../spec/format/README.md), раздел 24: `Set`, `While`, `TopLevelControl` и `GlobalReassign` включены, `Recursion` выключена, `load` запрещён, а встроенные имена — 33 имени `starlark.Universe` закреплённой версии, которые формат перечисляет. Условие проверки и выражения шаблона идут в том же диалекте (R88 spec; [текст формата](../spec/format/README.md), разделы 15, 23 и 24). Имена песочница держит своим перечнем, а не `starlark.Universe`: процесс вызывающего может дописать в него своё, и диалект от этого не меняется (R28).
- **Код** (R28) — `internal/sandbox`:
  - `CheckExpr(src, names...)` — выражение диалекта, которое называет только `names`, имена, которые связывает само, и встроенные имена: разбор `syntax.FileOptions.ParseExpr` и имена `resolve.ExprOptions` со своим перечнем. Ошибка — строка, столбец и слова go.starlark.net: `1:1: undefined: number`. Им `verdict.CheckPredicate` держит правило `task.predicate-expression`;
  - `Eval(ctx, limits, src, env)` — то же `CheckExpr` на именах `env`, затем разбор заново и `starlark.EvalExprOptions` на своём потоке, как шаги считают векторы. `Limits{Steps, Clock}`, ноль — без предела, а `Predicate` — 1 000 000 шагов и 1 с. Остановы — `ErrSteps`, `ErrClock` и `ErrPanic`, а отмена — ошибка `context`, обёрнутая; ошибка называет первую причину, как поток хранит первую причину `Cancel`, и только когда интерпретатор остановился по ней: вычисление, которое кончилось само, оставляет свой итог и свою ошибку. `print` ничего не пишет, а `Load` у потока нет;
  - `Compile(src, names...)` — то же `CheckExpr`, а затем программа из одного присваивания `_result = <src>`, собранная из дерева выражения, где имена — предобъявленные: она компилирует всё, что берёт `CheckExpr`, так же глубока для разбора go.starlark.net, как само выражение, и делает те же шаги, что `Eval`. `Func.Call(ctx, limits, args...)` — `Program.Init` со значениями имён по порядку на своём потоке, с теми же пределами, остановами и ошибками, что у `Eval`. Так выражения шаблона считаются на каждом сочетании без разбора заново: без предела шагов и часов, потому что шаги выражения подмножества ограничены его длиной (R32);
  - `CheckProgram(src)` — программа диалекта: разбор с опциями диалекта, ни одного `load`, а имена — свой перечень, как у `CheckExpr`. `Exec(ctx, limits, src)` — `CheckProgram`, компиляция и верхний уровень программы на своём потоке, после которого глобальные значения заморожены, как Starlark замораживает модуль: так `Program` решателя. `Program.Call(fn, args...)` зовёт её функцию на том же потоке, а `Program.Close()` кончает её часы и наблюдение за `context`: шаги верхнего уровня и всех вызовов — один счёт против одного предела, а часы одни — от `Exec` до `Close`. `Solver` — 100 000 000 шагов и 60 с. Остановы и ошибки — те же, что у `Eval`; после паники `Call` ничего не зовёт, а после `Close` отдаёт `ErrClosed`. Ошибку `context`, сделанного вызывающим, узнаёт `ContextDone` — его берут и вердикт условия, и решатель (R33);
  - поток — свой тип внутри пакета: предел шагов, часы, наблюдение за `context`, `recover` и первая причина остановки — один код на одно вычисление, `Eval` и `Func.Call`, и на программу со всеми её вызовами. Отмену поток видит на входе в каждую функцию Starlark, на возврате каждого вызова и на обратном переходе, так что часы, сработавшие между вызовами `solve`, останавливают следующий на входе.
- **Резерв адресов.** Импорт `go.starlark.net/starlark` на 64-битных linux и darwin резервирует 4 ГиБ адресного пространства под малые целые, а не вышло — пишет в `log` и считает медленнее (раздел 4). Это наследует каждый процесс, который импортирует `verdict`, — `api` и eval-раннер `tutor`: памяти резерв не берёт, а предел адресного пространства процесса его видит (R28).
- **CLI** проверяет решатели шаблонов по одному на CPU (`GOMAXPROCS`), каждый на своём потоке Starlark, а итог выводит в порядке шаблонов: `template.Instances` — функция на один шаблон, и её можно звать из нескольких горутин сразу. Пул держит сама проверка (R38): `module.Check(ctx, fsys)` раскрывает шаблоны модуля в `runtime.GOMAXPROCS(0)` горутинах, каждая берёт следующий шаблон по порядку путей, а итог встаёт по пути задачи, так что отчёт от числа горутин не зависит. `context` — вызывающего, у CLI его делают сделанным SIGINT и SIGTERM. `modulepackage.Build` берёт числа экземпляров у проверки, `module.CheckModule`, и решатель идёт один раз. С `context.Background()` и по одному идёт только `CheckFile`, файл сам по себе. Шаги потока от соседей не зависят. Стенное время и память у решателей общие: тяжёлые встроенные функции нескольких шаблонов сразу дойдут до часов или до предела памяти раньше, чем по одному.
- **Что известно из standalone** (раздел 4):
  - 25 000 000 шагов и 2 с на запуск, по одному запуску на vCPU и 3 с ожидания места; лимит шагов калибровали по 450 эталонным решателям, и худший потребовал 2 081 362 шага (R53 standalone);
  - его помощники платят шаг за каждые 16 байт и не строят списков длиннее 1 000 000 элементов: так шаги ограничивают и память помощников — 381 МиБ на потолке шагов, — а среде Go отдана девять десятых памяти экземпляра (`GOMEMLIMIT`);
  - но дыра памяти шире одного оператора. Оператор `*` и повторное `xs = xs + xs` строят огромный список мимо счётчиков; литерал `{}` в цикле держит по 512 байт на каждые девять шагов, и экземпляр с 1 ГиБ памяти был убит именно так; методы самих значений — `x.extend(range(3000000))` — берут три миллиона элементов за девятнадцать шагов (SPEC 6.6 standalone; R53 standalone);
  - отдельный процесс v1 standalone отложил, а четыре места с часами-страховкой отверг: «Verdicts depend on the load» (R125 standalone);
  - самый тяжёлый из его решателей — 2 413 617 шагов на версии standalone и 2 725 355 на 4f4267fb140d (R11).
- **Отложено:** память стороннего Starlark с этапа 4 — раздел 2.3.

### 3.5. Сравнение версий модуля

Новую версию модуля `module-kit` сравнивает с каждой опубликованной версией, снятые тоже, по правилам сравнения версий формата: принцип частей, таблица «изменение — часть версии», правило 0.y.z, сравнение проверки по смыслу, экземпляры шаблона по значениям параметров и восемь правил `module-version.*` — [текст формата](../spec/format/README.md), раздел 27 (R89 spec; R101 spec). Своих правил и своей таблицы у `module-kit` нет: их предложил R13, а формат 0.3 их принял, с поправками ниже, и векторы `vectors/versions/` держат их, как держат вердикт (R17). Версия модуля — semver `X.Y.Z` без пред-релизов и метаданных сборки (R46 spec); это не версия формата, MAJOR.MINOR, которую называет `module_format_version` (R44 spec). Код пишет эпик кода.

- **Чем формат 0.3 расходится с R13** (R101 spec; R17):
  - ID правил — с префиксом `module-version.`, а не по частям: `module-version.above`, `module-version.step`, `module-version.retired-complete`, `module-version.retired-kept`, `module-version.retired-known`, `module-version.ids-kept` и `module-version.languages-kept`, а восьмое, `module-version.bands-kept`, держит полосы: опубликованные полосы стоят первыми, по порядку и с теми же ID, а новая — только после последней;
  - та же версия с другим дайджестом — отказ `module-version.above`, а не `module-index.one-package`; правило индекса `module-index.version-above` держит то же при сборке индекса ([текст формата](../spec/format/README.md), раздел 26);
  - новая запись `retired_skills` — мажорная правка, вместе с упразднением, а запись только раскрывается: неверную в формате 0.3 не исправить;
  - у части есть ещё «нет»: не изменилось ничего, кроме версии, или новая версия — новейшая опубликованная как есть;
  - новая версия сравнивается с каждой опубликованной, и CI `modules` даёт `diff` пакет каждой (architecture 3.7 spec): поправка 2026-11-02 к R13, где `diff` брал остальные версии, только если их дали, держалась до ответа на В15;
  - через переход формата правила держатся по местам пакета, которые формат держит во всех версиях, а часть, пока формат v0, — мажорная ([текст формата](../spec/format/README.md), раздел 2). Навыки и ID через переход `diff` сверяет так же, как внутри одной версии формата.
- **Что сравнивается** — пакеты, а не YAML автора: канонический вид и список части для устройства (раздел 3.2). Новая версия — папка модуля, которую `diff` проверяет и собирает в памяти, или пакет, уже собранный `build`. Опубликованные версии — пакеты файлами, каждый сверен по цепочке дайджестов от индекса. Пакет прошлой версии формата — только `inventory.json` и `server.json`, которые `diff` читает по местам, которые формат держит во всех версиях. Что в пакет не входит — комментарии, порядок ключей, `eval/`, файлы на `.`, — версии не меняет: пакет тот же.
- **Команда `diff`:**

  ```
  module-kit diff [--json] (--index <module-index.json> | --first) [--published <папка пакета>]... <модуль>
  ```

  - `<модуль>` — папка модуля или папка пакета; их различает `manifest.yaml` или `inventory.json` в корне. Папку модуля `diff` проверяет и собирает, как `check` и `build`, и никуда не пишет; пакет, собранный `build`, избавляет CI от второй проверки с решателями;
  - `--index` — `module-index.json`, который CI уже сверил рецептом `release-verify`: подписей CLI не проверяет (R77 spec). Индекс он читает по местам, которые формат держит во всех версиях ([текст формата](../spec/format/README.md), раздел 26), — `moduleindex.Read` (R35), — и берёт из него все версии модуля и их версии формата. `--first` говорит явно, что опубликованных версий нет, как сборка индекса без прошлого (поправка 2026-11-02 к R63 spec): пропущенный файл молча не пройдёт;
  - `--published` — папки пакетов файлами ([текст формата](../spec/format/README.md), раздел 25), без `device/`. Пакет `diff` узнаёт по дайджесту байтов `inventory.json` — это дайджест пакета, — а затем сверяет `server.json` и, в текущей версии формата, `device.json` по описи. Лишние папки он пропускает, а пакет каждой версии, которую называет индекс, нужен: без него сравнить нельзя;
  - код 0 — версия принята, модуль не изменился или это первая версия: `--first` или индекс, который модуля не называет (R40); 1 — отказ: строка на каждое нарушенное правило, `refused: <ID>: <слова>` (R37), или отчёт проверки модуля, как у `check`, если её отвергла проверка; 2 — сравнить нельзя: вызов, ввод-вывод, разорванная цепочка дайджестов, нет пакета версии, которую называет индекс;
  - отчёт: модуль, новая версия, с какими версиями сравнено, найденная часть, допустимые следующие версии и поднятая часть. Затем изменения, по строке: часть версии, путь — JSON Pointer в каноническом виде или в списке части для устройства, — и что изменилось; у экземпляров — значения параметров. С `--json` — тот же отчёт данными;
  - в сеть CLI не ходит: индекс и пакеты кладёт CI `modules` (architecture 3.7 spec).
- **Библиотека** — одна функция над проверенными пакетами — новым и опубликованными — и индексом; CLI её обёртывает, а с этапа 4 её зовёт `module-registry` (R17 spec). Ту же «ту же мажорную» читает `api`, переводя ученика на новую версию (architecture 3.5 spec).
- **Код** (R36) — пакет `moduleversion`:
  - `Compare(next, published)`: `next` — `*modulepackage.Package` новой версии, `published` — `[]Published{Digest, Files}`, пакеты файлами без `device/`. Каждый читает `modulepackage.ReadParts` по цепочке дайджестов — опись, `server.json` и `device.json`, без файлов части для устройства. Новейшая — по semver, снятые тоже; та же версия с тем же дайджестом — `Unchanged`, и ничего не сравнивается; без опубликованных — первая версия. Ошибка — пакет, который `ReadParts` не принял, пакет формата 0.2 — `ErrFormatVersion`, пока его не читает T36, — пакет другого модуля и два пакета одной версии;
  - `Changes(before, after)` — часть и изменения двух пакетов одного модуля и одной версии формата. Каждая строка таблицы [текста формата](../spec/format/README.md), раздел 27, — у своего места, как у `versions.mjs` `spec`, а всё прочее, кроме `manifest.version`, — патч у каждого места, где JSON-значения `server.json` и `device.json` разошлись: по членам и элементам, а `instances` шаблона — целиком. Разница у места строки таблицы или под ним не пишется, а под `skill_tiers` и `instances/<ID>` — когда разошлись граф навыков или сама задача. Проверка сравнивается по смыслу через `normal.Compared` и `normal.Units` — их же зовёт `verdict`; ячейки — по месту в пункте, `answer_slots/<j>` на листе и `line/<k>` в тетради; экземпляры шаблона — по числам параметров, через `template.Instance` каждой версии;
  - `Steps`, `StepPart` и `SameMajor` — правило 0.y.z: следующие версии после версии и часть каждого шага, часть шага к версии — `None`, если она не следующая, — и та же ли мажорная у двух версий, как её читают `diff` и `api`. Числа поднимает `semver.Version.Raise`, текстом и без границы;
  - отчёт — `Comparison{Module, Version, Published, Newest, Unchanged, Part, Next, Raised, Changes}`: `Next` — следующие версии, чей шаг поднимает часть не ниже найденной, `Raised` — часть шага к новой версии. `String()` пишет строку модуля и версий, найденную часть, следующие версии и поднятую часть, а затем по изменению на строку — как нарушение проверки модуля: `server.json #/tasks/apples: minor: the task apples is added`, у экземпляра — `on the instance a = 2, b = 3:` перед словами. Изменения идут по части от мажорной, затем по месту: `server.json` до `device.json`, а в файле — `schema.ComparePointers`. С `--json` — тот же `Comparison` через `encoding/json`: `module`, `version`, `published`, `newest`, `unchanged`, `version_part`, `next_versions`, `raised` и `changes`, у изменения — `part`, `file`, `pointer`, `parameters` и `what`, а часть — своим словом;
  - правила (R37) — `Comparison.Breaches`, по `Breach{Rule, Message}` на нарушение, и `Refused()`; `Rules` — восемь ID в порядке [текста формата](../spec/format/README.md), раздел 27. `module-version.above` — по каждой опубликованной версии, снятые тоже; `module-version.step` — по новейшей, только если `above` пропустил, по `Raised` и `Part`; остальные шесть читают только места, которые формат держит во всех версиях, — языки, ID полос по порядку, ключи навыков, задач, уроков, ловушек и приёмов, `retired_skills` с `replaced_by`, — так что держатся и через переход формата. Отчёт пишет каждое нарушение строкой `refused: <ID>: <слова>` перед изменениями, а `--json` — `breaches`. Слова — как у `versions.mjs` `spec`;
  - переход формата (R37): опубликованный пакет, чья опись называет более раннюю версию формата, читается по цепочке — `inventory.json` по дайджесту, `server.json` по дайджесту и размеру из описи — и только по местам: `Changes` его не сравнивает, а часть — мажорная, пока формат v0, одним изменением `inventory.json #/module_format_version`. Пакет более новой версии формата — `ErrFormatVersion`: его мест формат ещё не обещал читателю этой версии. Пакет без места, которое формат держит, — `ErrNotCanonical`;
  - печатает отчёт команда `diff` (T38; R40) — `cmd/module-kit/diff.go` и `published.go`: версии модуля — из `moduleindex.Read`, пакет каждой — среди `--published` по `package_digest` записи, `moduleversion.Published{Digest, Files}` из папки; с `--json` у модуля, которого отвергла проверка, — `{"check": [...]}` с путями от папки командной строки.
