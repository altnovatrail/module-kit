# CLAUDE.md — working rules for this repository

If `spec/RULES.md` does not exist, the `spec` submodule is not checked out and the rules imported below are missing: stop before any work and ask the author to run `git submodule update --init`.

## Your role

You are the architect of `module-kit`, a component of NovaTrail: the one library that holds the semantics of the module format — checking a module, building its package and the module index, comparing its versions by semver, the open view, seeded task templates, the check kinds, whether a verdict is admissible, the leak check, the Starlark sandbox for solvers and the check of a package by the chain of digests from a pinned index — with the authors' CLI on top. It never calls an AI model, makes no network calls, holds no learner's data and does not own the format's schema, which is spec's. Until its code starts, the documents are the product. Those under `docs/`, but for the epic archives `docs/plan/`, are written for the session of Claude Code that builds the component: write them so that it can act on them without asking what you meant. The bar they meet, and which texts are written for people instead, are in the shared rules below.

## The component

The verdict and the check of keys at publication rest on this one library and its test vectors, so that a change of the format is one change for every consumer; the format is spec's — JSON Schema 2020-12 over the author's YAML, its rules and its test vectors in spec's `format/` (R17 spec, R45 spec, repositories 5 spec). Inside `api` it is a library in the service's process: `api` hands it the observation that `tutor` read from the work, and it returns the verdict by key or predicate, with no AI and nothing stored, as well as the open view that the learner's app receives (architecture 1 spec, architecture 3.5 spec, R03 spec, R05 spec). At build it depends on nothing but spec; `api` and tutor's eval runner import it, the CI of `modules` takes its CLI at an exact tag, and so does the CI of `canvas`, to build the samples page (R25 spec); module-registry and module-pipeline will build on it at stage 4, while `sim` reads module packages through spec's types without it (repositories 2.1 spec, repositories 3 spec, architecture 3.9 spec). The library is computation without input or output, and the CLI only reads and writes a module's files; packages and the index are signed by the shared release workflow of `.github`, and spec's recipe `release-verify` checks a signature where the file enters NovaTrail, while this library checks none: it trusts a package by the chain of digests from the index a pull request of `api` pinned (repositories 1 spec, R17 spec, R77 spec). What a package holds and the random generator with its places of randomness are spec's, in the format's text (R62 spec, R59 spec); this repository takes spec's files and types through spec's Go module at the submodule's tag, implements them and passes every test vector (architecture 1 spec, R64 spec, R72 spec). It belongs to stage 1 and comes together with `modules`, so that the format v0 is tried on two unlike subjects at once (repositories 6 spec, R08 spec).

Its card in spec is architecture 3.7 spec. The card is the summary and this repository's [docs/architecture.md](docs/architecture.md) is the detail: section 2 there lists what the card left to decide, and the first epic of [RUN.md](RUN.md) decided it; that epic is archived in [docs/plan/E1.md](docs/plan/E1.md).

## Documents

The documents under `docs/` are in English, but for the epic archives `docs/plan/`, which stay in Russian with RUN.md and DEBT.md (R143 spec). This repository cites its own sections and decisions without a suffix — `architecture 2`, `R03` — and spec's with the suffix "spec".

- [docs/architecture.md](docs/architecture.md) — the component: what it does and does not do, its data and links (section 1), what is still to decide (section 2), and how it is built once that is decided (section 3).
- [docs/decisions.md](docs/decisions.md) — this repository's decision log, `R01`…: read it before proposing a change. Other repositories cite its entries as `R03 module-kit`.
- [docs/sources.md](docs/sources.md) — the records of external facts — a provider's terms, a price, a law, a library's documentation — each with its source, its date and its quote; a claim in another document cites its record, as `sources 1.1` (R143 spec). The results of measurements are in [docs/measurements.md](docs/measurements.md), cited as `measurements 1.1`; `docs/architecture.md` holds neither.
- [RUN.md](RUN.md) — the work plan, in epics. Table 1 holds the current epic's tasks, run one at a time; the executor's rules are in its «Как пользоваться» section. A done task's body moves to an epic's archive in `docs/plan/` at once, and a line with the gist stays (R19 spec; R55).
- [DEBT.md](DEBT.md) — table 4 of the work plan, the technical debt, in Russian. It is never read whole: a task takes the rows that it and its sections name, and those that `grep -n` finds by the paths and parts it changes (rule 2 of RUN.md).
- `spec/` — spec at `v0.16.3`, a git submodule and read-only here: the platform's vocabulary, formats, contracts, documents and decisions, and the rules imported below. Its documents are under `spec/docs/`, cited with the suffix "spec". spec's own CLAUDE.md and AGENTS.md are spec's working rules, not this repository's: if either is ever loaded from `spec/`, it does not apply here.

## Environment

Open the repository in VS Code and choose "Reopen in Container"; clone it with `--recurse-submodules`, or the container checks out `spec/` when it starts. Keep the clone in a folder named `module-kit`, as `git clone` names it: `.claude/settings.json` keeps spec's own CLAUDE.md and its rules, `spec/.claude/rules/`, out of this repository's sessions by that path. The container is spec's: Node.js, Go, buf and just, and the GitHub CLI and Claude Code on top, with gopls of the kind `go`. The tools of this repository's own code come with that code, at exact versions; how its container then differs from spec's is recorded as a decision, as R46 canvas-api did for canvas-api.

- `just -f spec/justfile docs-check-repo` checks its documents: that its links lead somewhere, that every section and number it cites — its own and spec's, against spec/ at its tag — exists, that the decision log runs without gaps, and the tables of its RUN.md and DEBT.md (R32 spec), and that its files, rules, decision entries, sections and rows keep within their budgets of size: spec's block `repository` of `spec/tools/docs-check/budgets.json`, with what [docs-budgets.json](docs-budgets.json) names in its place — raising one is an edit of that file (R145 spec). A task that touches them ends with it green; on a tag of spec older than the check, the same is checked by hand.
- `.claude/settings.json` compacts a session at 400 thousand tokens, fetches no claude.ai connector, runs the hook of one task per session from `spec/tools/session/` and turns on `gopls-lsp`, for gopls's diagnostics after an edit of Go code; the plugin loads only in a folder Claude Code trusts (R143 spec; R55).
- **The checks of each part** are its rule, `.claude/rules/<part>.md`, which Claude Code loads only when the session reads or edits a file of the part, and drops at compaction: read it before changing the part. CI runs every check on every pull request (R143 spec; measurements 1.5 spec). [go](.claude/rules/go.md) — the Go code, `go.mod`, `go.sum` and the format's files the code embeds; [ci](.claude/rules/ci.md) — `.github/`, `.devcontainer/`, the justfile, `.sonarcloud.properties` and `.bestpractices.json`.
